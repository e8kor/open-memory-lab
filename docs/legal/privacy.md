## What the service is

Open Memory Lab stores short notes that people and AI agents ("memories") and lets an agent
recall the ones that a second identity has reviewed and approved. A memory an agent writes is held
where others cannot read it until a reviewer who did not write it approves it. You reach the
service from Claude as a custom or directory connector, from the `oml` command line, or from a
browser page.

## What the service collects

| Data | What it is | Where it comes from |
|---|---|---|
| **Memories** | The text of each note, its kind, its claim key, optional source (repository, path, revision), optional validity dates, an origin kind, and any attached file | What you or your agent write through the `Remember` tool, the command line or the API |
| **Recall questions** | The words an agent searches for | The `Recall` tool and the API. By default only a digest of the request is kept. The text is kept only if an administrator of your organisation turns it on (see Retention) |
| **History of acts** | A signed, attributed record of every write, review verdict, approval, removal and key or access change: who (key and principal name), what, when, in which workarea. It carries digests, not memory text | Generated by the service |
| **Keys and access** | Key names, principal names, roles, the workareas a key can reach, crew names; key values are stored only as SHA-256 digests | Your administrator, when issuing a key |
| **Connections** | For a Claude connector: the OAuth client's identifier and redirect address, the state of the connection, and access and refresh tokens stored only as digests. A connect code is stored only as a digest | Your sign-in to the connector |
| **Web sign-in** | For people on the administrator's allowlist: an email address, the user name it maps to, the Google or GitHub account identifier pinned at first sign-in, and a session token stored only as a digest | The administrator's allowlist and the provider you sign in with |
| **Request logs** | One line per request: time, route, status, duration, a request identifier, the client IP address, the key name and principal, the user-agent string, and for a connector call the tool name, its mode and its outcome. A line never holds the text of a memory, a recall question, a tool's arguments or a secret | Generated by the service and, in front of it, the reverse proxy |
| **Usage measurements** | For each recall: the pipeline used, the number of hits, and what the reader did next (opened a hit, searched again). Counts per day may be summarised in an analytics copy. No memory text | Generated by the service |
| **Metrics** | Counters and timings with fixed labels. No memory text, no question text, no principal names | Generated by the service |

The service reads only what a tool call carries. It does not read your Claude conversation, your
Claude memory, your chat history or your files; it receives the arguments Claude sends when you
or Claude call one of its three tools (`Remember`, `Recall`, `Workarea`), and nothing else.

## Why it collects it

- To store memories, hold them for review, and serve approved ones to the people and agents
  allowed to read them.
- To prove who did what: the history of acts exists so that a reviewer is never the author and a
  decision can be checked afterwards.
- To keep the service secure and running: the request logs and metrics are used to find faults,
  limit abuse and respond to incidents.
- To measure whether recall helps its readers, in aggregate, with no memory text.

The service does not sell personal data, does not show advertising, and does not use memories to
train models. The software makes no call to a third-party model or AI provider with memory text:
search and reranking run inside the service. [Operator to confirm for the hosted deployment.]

  your organisation can read every memory in it, and each such read is recorded.

## How long it is kept

| Data | Kept |
|---|---|
| Memories | Until a person removes them. Nothing expires on its own. A removal either hides a memory while keeping its bytes (demotion) or destroys the key that makes its text readable (erasure) |
| History of acts | Permanently. It records who acted and when, and it survives an erasure of the memory it concerns. Its digests do not reveal memory text |
| Request logs | At most 30 days. The operator's log tooling enforces the limit, and the reverse proxy's access log falls under the same limit |
| Recall usage measurements | 30 days. Daily counts in the analytics copy cover the last 30 days |
| Recall question text | Not kept unless an administrator turns it on; turning it off clears the text kept |
| Connect codes | Ten minutes, or for a code an administrator issues for a reviewer, up to 30 days. A code is spent on its first correct entry |
| Access tokens, refresh tokens | One hour and 30 days from the connection being made |
| Web sessions | Until sign-out or expiry |
| Backups | The service keeps no scheduled backup at the time of writing, so there is no backup copy of your data and a lost disk loses it. [Operator to update this line if backups are introduced, with the period they are kept.] |
| Analytics copy (lake) | Memory bodies in it are encrypted under per-memory keys and become unreadable when a memory is erased. [Operator to confirm whether the hosted service runs the lake writer.] |

## Your choices and rights

- **Remove a memory.** Ask the person or administrator who owns the workarea. Erasure destroys the
  ability to read the text; the history keeps the fact that an act happened.
- **Disconnect Claude.** Remove the connector in Claude's settings. An administrator can also end
  the connection on the service.
- **Ask about your data.** Write to the privacy contact above to ask what the service holds about
  you, to correct it, or to ask for its erasure. [Operator to state the response time and the
  rights that apply in each jurisdiction served.]
- **Complain.** You may complain to your data-protection authority.

## Security

Key values, connect codes and tokens are stored only as digests. Each organisation's rows are
separated by the database on every table. The history is signed and chained so tampering shows.
Report a vulnerability privately through the project's private vulnerability reporting, not in a
public issue. No system is free of risk, and the service is pre-release software.
