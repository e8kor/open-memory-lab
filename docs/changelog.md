# Release notes

Newest first. Each release is a signed tag on the [releases page](https://github.com/e8kor/open-memory-lab/releases).

## 0.7.3

Released 2026-11-13.

**v0.7.3 is usage metering, limits on keys and the console redesign.** Every account is counted by its own writes and held to the limits of a named quota profile ([ADR-0071](adr/ADR-0071-every-account-is-metered-by-counters-the-write-updates-in-its-own-transaction-and-named-quota-profiles-set-its-limits.md), migration 0045), which merged to `main` after v0.7.1 and ships here for the first time. A key can end on a date and carry a request rate of its own ([ADR-0079](adr/ADR-0079-a-key-ends-on-a-date-and-is-held-to-a-request-rate-both-set-at-issuance-and-changed-only-by-an-admin-key-that-is-not-the-key-itself.md), migration 0046). A memory is started in a person's root by that person's keys only, so a tenant key's new memory there is refused as `submission.user_root_refused`. A web session key an admin denied issues no key, and every signed-in page draws Sign out. The console is redrawn on two sides, Personal and Administration, each with its own bar and navigation, with one workarea picker on Memories, the Atlas and Review, and a Review page that lists every held fact the way Memories does, with **Open to judge** on the person's side. Console, docs and landing copy are in the neutral voice: no "you", "your" or "my". The held listing's store calls no longer grow with the number of workareas. **Four things belong to the upgrade:** migration 0045 runs at boot under locks on `memories`, migration 0046 adds two columns to `api_keys`, a tenant key that writes into a person's root is refused from the first request, and a quota profile is configured before any account is limited. The upgrade notes close this section.

Pinned every GitHub Action in `.github/workflows/` by full commit SHA with its tag in a trailing comment, one commit per action across all workflows, the newest tag of the major each already used, and added `scripts/lint_practices.py actions` to the practices workflow's lints job: it fails an unpinned `uses:`, a missing tag comment and two commits for one action (#264). The weekly dependency pass runs `scripts/check_action_updates.py`, which reports a pinned action with a newer tag of its major and prints a newer major without failing; [CI and toolchain](contributing/ci-and-toolchain.md#pinned-actions) says how to change a pin. The SDK publish lint now also refuses a step-level `if:` in the two publish jobs, an upload before the checksum step, `npm --flag publish`, `npx npm publish`, `pnpm publish` and `yarn publish`, `packages-dir`, `repository-url` and `password` on the PyPI action, and a checkout of anything but the tag; the PyPI job uploads the default `dist/`, which holds only the two checked files (#184). Both SDK packages are named `open-memory-lab-sdk` on PyPI and npm, the operator's choice of 2026-11-12; the Python import name stays `oml_sdk`. Publishing stays off until the operator sets `PUBLISH_SDKS`. [Releasing](contributing/releasing.md#publishing-the-sdks) says that `True` and `TRUE` turn it on as `true` does, and lists what a shared server needs before a release that contains ADR-0076, a new scanner rule set or a migration that rewrites `memories`. The [settings page](operations/configuration.md#limits-counted-per-process) states that the per-key request rate (120 a minute) and the per-address sign-up count (5 an hour) are counted per process, so N processes admit up to N times each; the thirty-day measurement of the defaults is still open (#164). The pin lint parses each workflow as YAML, so a `uses` key in a flow mapping, a quoted key, a value on the next line, an anchor or a merged mapping is read, and a sub-path of an action at another commit is the same action at two commits. The publish lint lets the PyPI action take `print-hash` and no other input, so the underscore spellings, `user`, `skip-existing` and `attestations: false` are refused with the rest; it requires the registry-name step and the checksum line to be written whole, with no `||`, `&`, pipe, `if` or `echo` around them; and in the PyPI job it refuses a glob, `mkdir -p`, any other line that fills `dist/`, and a step between the checksum and the upload. The weekly check verifies that each pinned commit is the commit of the tag its comment names, reads a comment that names a major alone, and its log, with the newer-major lines, is printed in the job whatever it returned. `sigstore/cosign-installer` is pinned to v3.9.1, the commit the v0.7.1 release signed with (cosign v2.5.2), so the weekly check reports it as behind by design.

**Web console.** A memory's card says when it was approved and whether a person's key, an agent's key or a service's key approved it, in place of "approved by a key outside its lineage" (ADR-0077 d2, #175). A person approving their own agents' write is marked a self-review. A card the API serves no approval for, such as a shared `universe` row or the admin list, says "approved" and nothing more; an unreviewed card names no approval. The Rust SDK's `Memory` carries `approved_at` and `approver`.

**Web console.** The Memories JSON routes (`/web/data/memories`, `/web/admin/data/memories`) carry `approved_at` (the timestamp, as on the API) and `approver` (`kind` person, agent or service, and `same_user`) for each row, null where the HTML card says only "approved" or is unreviewed, so the data and the page cannot differ (ADR-0077 d2).

**Web console.** The Rust SDK's `Limits` reads every quota as `Option<u64>`, since the API's serialiser writes null for any quota that is unlimited (ADR-0071 d5). Configuration bounds `memories`, `keys`, `connections` and `requests_per_minute` at 1,000,000, so on a configured deployment only `text_bytes` and `writes_per_month` are null. The usage card draws an unlimited meter as a count with no bar and no mark, and an unlimited request rate as a dash.

**Web console.** The Start page and the Keys page draw a "Usage" card, and the users page draws the meters as columns (ADR-0071 d6, #321). The five meters `person` on `GET /v2/whoami` and each row of `GET /v2/web/users` carry are shown with their count, their limit where one holds, and a mark at 80% of the limit and at the limit: memories, text stored, writes this month, keys and connections, with the request rate beside them on the card. The users page draws a mark only on a row whose `under_quotas` is true. A person whom no limit is read for gets no card, and a meter an older API does not serve is left out, never shown as zero. The profile's name, the month and the recall count are not on those fields and are not shown, so a console session needs a route or fields for them (ADR-0071 d6, amended). The Keys page reads the person beside its key list in the same round; a failed read marks the card unavailable and the keys still draw. The Rust SDK's `Usage` and `Limits` carry `text_bytes`, `writes` and `writes_per_month`, and `Client::whoami_person` asks for the person block.

**Keys.** A key can end on a date and be held to a request rate of its own (ADR-0079, accepted 2026-11-12; #323; migration 0046). `oml keys issue` and `oml keys issue-agent` take `--expires <instant>` and `--requests-per-minute <n>`, and `POST /v2/keys` takes `expiry` and `requests_per_minute`; the `expiry` it used to refuse by name is served. From its expiry on a key answers `401 auth.invalid` with `details: {reason: "expired", expiry}`, where an unknown or revoked key answers `unknown`, and only the holder of the key's own credential is told. A connector key's expiry is its connection's: the access token is refused the same way at `/mcp`, a refresh answers `invalid_grant`, and a connect code asked for it is `oauth.connect_refused` with `reason: expired`, as ADR-0031 d11 decided. The expired key's row, grants and name stay; `GET /v2/keys/{key}` and each item of `GET /v2/keys` serve `expiry`, `expired` and `requests_per_minute`, `GET /v2/whoami` serves the calling key's, and `oml keys show` prints them, as `oml keys issue` and `oml keys issue-agent` do for the key they issue, `issue-agent` on stderr beside the key it names; `oml keys show` calls an expired key `revoked: no (expired)`, never live. The request past a key's rate answers `429 limit.rate` with `Retry-After` set to the seconds left in the UTC minute; a key of an account under a quota is held to both rates, the key's own counted first, so a request the account's rate refuses still consumes one of the key's own. Each server process counts alone, so n processes admit up to n times the rate, as the settings page states for the account rate. `oml keys limit <key>` (`POST /v2/keys/{key}/limits`, journalled as the new `key.limits_set`) moves or clears either limit for an admin key that is not the key itself: any other role is `access.verb_ceiling`, and the calling key, a session key, a revoked key and an admin key are `request.validation` with `details.reason`, so no key extends its own date or raises its own rate. An admin key carries neither limit: issuing one with `expiry` or `requests_per_minute` is `request.validation` with `details.reason: admin_key`, as is a limits change naming one, so no key that can change a limit carries one, no admin key ends another by a date, and no admin key is temporary. Moving an expired key's date later makes it authenticate again. `oml doctor` fails for an expired key with its date, warns for a key past its rate, and otherwise names the instant the key ends and the rate it is held to. Every existing key keeps no expiry and no rate. Not built: a mark for an expired key on the web console's keys page, and a count shared between server processes.

**A memory is started in a user's root by that user's keys only** ([ADR-0044](adr/ADR-0044-every-user-works-under-a-root-of-their-own-and-universe-serves-curated-claims-without-their-source.md) d16, an amendment the operator accepted on 2026-11-12; #329). A tenant writer key holding a subtree grant on `universe`, or any grant inside a user's root, could start claims in `universe.<user>`; with usage metering that moved a person's `memories` with no check against their ceiling. A new memory there by a key that is not that user's is now refused `409 submission.user_root_refused`, on `POST /v1/memories` and on `oml_write`, and journals nothing. A reviewer granted there, a tenant key or another person's review key, still proposes a successor or a retirement of a served memory, as the admin page does; the one successor refused from it is that of a ratified retirement, which would put the claim back in service and on the user's `memories`. A person's session keys are their keys: `<user>-review` and `<user>-curate` carry no `user` and name their person by their session, and the rule reads a key's person the one way `same_user` does, so a person's review key puts a retired memory of theirs back, on the admin memory page as well, and is still refused in a root an admin only designated it to review. The code is answered only where the key reads the workarea or the target; a key that reads neither keeps `access.not_found`. Reads, recall and review there are unchanged, and nothing already written is touched: versions tenant keys wrote there before stay served, reviewable and under the accounting [ADR-0071](adr/ADR-0071-every-account-is-metered-by-counters-the-write-updates-in-its-own-transaction-and-named-quota-profiles-set-its-limits.md) d3 states, whose sentence now says no new write produces that case. The strict rule, every claim write from the user's keys only, was built first and rejected by the operator on 2026-11-12. `oml doctor` under a tenant writer key whose default workarea lies in a user's root warns and names the key to issue instead. Grants are unchanged, so `my_effective_verbs` still lists `remember` and `learn` for such a key. A user's own keys can still put a retired claim back past their `memories` limit, and so can the ratification of a put-back another key proposed there before this release and that is still held, since the rule is checked at the proposal (#340). [errors](api/errors.md), `openapi.yaml`, [roles and keys](architecture/roles-and-keys.md) and [workareas](architecture/workareas.md) carry the rule, and both SDKs' generated layers the new code.

**Web console and API.** A session key an admin denied no longer issues a key (#325; ADR-0070 d2, d8, an amendment the operator accepted on 2026-11-12). `POST /v2/keys` as `<user>-web`, `POST /v2/keys/{key}/connect-codes` and `POST /v2/keys/{key}/denials` as a session key read the key's access when they run and refuse one that carries a denial, on any workarea, with `access.verb_ceiling`, `details.reason: session_key_denied`, journalling nothing. Before, a `<user>-web` key denied on `universe` still issued a key holding the person's whole root with no denial on it. The refusal is permanent and any denial brings it, one on a workarea outside the person's root included: no verb lifts a denial, and removing the person's address and adding it back leaves the same `<user>-web`; from then on an administrator issues, connects and cuts off that person's keys (the operator's decision of 2026-11-12, recorded in ADR-0070 with the narrower rule it rejects). The Keys page and the Start page show the refusal by its code and message. `POST /v2/web/session/end` and the lead's sign-out read nothing of the key, so a denied person still signs out; they also still sign in and see their keys. Each of the three acts costs one more resolution of its key (two store calls for `<user>-web`, one for `<user>-admin`); no `GET` gained a read. Each reads the chain head before that resolution and commits on that head, so a denial committed while the act runs is never followed in the journal by a completed act: the commit conflicts and the retry is refused. An issuance without a connect code is several commits, the key and then its grants; a commit that lands between them, a denial included, leaves `key.issued` and then `key.revoked` for the half-issued key, whose value is never returned. An issuance with a connect code is one chain and leaves nothing. An act refused before its commit now reads the head first. Not changed: a denied `<user>-web` still asks for the person's deletion and reads their export (#335 asks whether it should).

**Web console.** Every page a signed-in person is shown draws **Sign out** in its header, a refusal page included: a page not found, a form refused, an API refusal shown by its code, and the refusal a cut-off key's act answers (#327; ADR-0070 d2, d3, d5, an amendment the operator accepted on 2026-11-12). The sign-in page, the sign-up terms page and a refusal the server answers before it reads the session draw none. No page offered it before, so a session ended only by expiry, a change to the person's allowlist entry or a new sign-in. The control is a form that posts `sign_out` with the session's CSRF token to the server's `POST /web`, never a link: the server ends the session, so every credential `oml-web` derives from it is `auth.invalid` from the next request, clears the session cookie with the attributes it was set with and returns to the sign-in page. Below 600px the header drops the name and keeps the control. `POST /v2/web/session/end` still serves no page. The header was looked at in Chromium as a static render at 1100px and 390px, before the control's container became a `div` and before the refusal page drew it; neither was looked at since, and the running console was not.

**Web console and API.** A person whose `<user>-web` key carries a denial keeps their export and their deletion request (#335; ADR-0070 d2, a decision the operator took on 2026-11-12, "Keep both", and confirmed the same day). `GET /v2/web/export` and `POST /v2/web/deletion-requests` read nothing of the key's grants or denials, before or after the decision, and now tests hold each: with a denial on `universe`, on the person's root and on a workarea outside it, the export answers `200` with what it served before the denial, and the deletion request journals `web.deletion_requested` under the denied key; the Start page draws the export link and the deletion form for that person and downloads and files through them. The export serves every memory in the person's root and below, every state, and the person's keys. After a denial on `universe`, on the root or on a workarea inside it, that includes text the same key is refused through `GET /v1/memories/{artifact_id}` (`access.not_found`): a test holds a memory in `alice.notes` in the export of a key denied there, text and all, beside the `404` for the read by its id. A denial on `<user>-web` denies none of the person's agent keys, and the deletion request ends nothing and changes no access. Without the two routes a person whose session key is denied has no way in the console to take their memories out or to ask for their account to end. The alternatives the operator was offered, keeping the deletion request and refusing the export, and refusing both, are recorded in ADR-0070 with the decision. No behaviour changed. The administering guide and the roles-and-keys page say the two still work.

**Web console and API.** A person whose `<user>-web` key carries a denial on any workarea is told so on the Keys page and the Start page, and neither draws the forms for the three acts that key is refused for good (#343; ADR-0070 d2, d5 and d8, the amendment "A denied session key's pages", which also amends ADR-0039 d15; the operator accepted it on 2026-11-12 for the web session key only). The Keys page draws no **Issue key**, **Issue connector key**, **New connect code** or **Cut off**; the Start page draws no **Issue my credential**; each shows one sentence in their place: "Your web session is restricted: you cannot issue keys, get connect codes or cut off keys. An administrator can do these for you.", with a muted line under it saying that exporting your memories, requesting deletion and signing out still work. On the Keys page the sentence comes first, above the table, and the row of the session's own key is marked **restricted**, where it read `live` for a denial that is not on `universe`; no other key's row gains a state. Before, the pages drew the forms and each answered the 403 `access.verb_ceiling`, `session_key_denied`, every time; `GET /v2/keys` shows `cut_off: false` for such a key when the denial is not on the whole root, so nothing the page read told it. The page now reads one served field: `GET /v2/whoami` carries `denied`, a boolean, on the record of a person's `<user>-web` session key, true when the key holds a denial in force on any workarea. It names no workarea, count, author or time, and it is absent on every other key, `<user>-review`, `<user>-curate` and `<user>-admin` included, so an agent key or an admin key still learns nothing of its denials (ADR-0039 d15 as amended). The field comes from the access the session gate already read, so no read gained a store call: the five calls the two pages make cost 2, 2, 12, 4 and 8 store calls before the field and the same after it, with and without a denial on the key. The store-call counts are unchanged; one test was added to the `web_console_reads` suite, which holds them equal before and after a denial. The page test holds the page equal to the API's answer: each act sent anyway is the 403 the page drew no form for. `openapi.yaml`'s `Whoami` and both generated SDKs carry the field; no operation was added. The pages were not looked at in a browser.

**Web console.** The Keys page, the admin's Keys page and the admin's People page mark an expired key and show its date and its rate (#337; ADR-0079 d2, d3, d4). Each key's row draws **expired** in the place and chip it draws `revoked` and `cut off`, the instant it expires or expired beneath its role, to the second and in UTC by name (`2026-10-29 12:30:00 UTC`, the instant as served in the element's `datetime`), and "N requests a minute" for a key that carries a rate of its own; a key with neither shows neither, and an admin key never carries either, so its row shows none. A key that carries two marks, such as `cut off` and `expired`, draws them apart, with a comma between them for a screen reader. Before, the pages read `revoked` and `cut_off` alone, so a key past its date read as live. An expired connector key is not offered **New connect code**, which the API refuses with `oauth.connect_refused` and reason `expired`; the row says "Expired: no new connect code until an admin sets a later date." instead. **Cut off** stays on an expired key: a denial is not refused on one, and an admin can move the date later. The page reads `expiry`, `expired` and `requests_per_minute` from `GET /v2/keys`, which already served them; no call was added. The page test holds each row equal to the API's fields for a key with both limits, a rate of one, an expired key, an expired connector key, a key with neither and the admin's own admin key. The pages were not looked at in a browser.

**Web console and API.** A person sets an expiry on a key they issue themselves (#352; ADR-0079 d1, d5 and the operator's answer 3, built on the operator's word of 2026-11-12). `POST /v2/keys` as a person's `<user>-web` session key admits `expiry` under the rule of every issuance, an RFC 3339 instant with its offset, later than the server's clock, and still refuses `requests_per_minute` as `request.validation` naming the member. The Keys page's two issue forms, for an agent key and for a connector key, each carry one optional date input, **Key expires (optional; end of that day, UTC)**, which works without script; the page sends the day as its last second in UTC (`YYYY-MM-DDT23:59:59Z`), and a day that has passed or a value that is not `YYYY-MM-DD` is refused on the page as the API refuses the instant, with its status, code and message; a day its month does not hold, such as `2026-11-31`, is read as the day that many days on, as every `date-time` of the API reads it. Changing or clearing the date afterwards stays with the admin key role: a person's session key is still `access.verb_ceiling` on `POST /v2/keys/{key}/limits`, and the page says "only an admin can change it later". The Start page's one-button issue sets no date. Before, a person's own issuance refused `expiry` by name, so only an admin could date a person's key. The Rust SDK's `issue_key` takes the optional instant; no operation was added, and the CLI is unchanged. The pages were not looked at in a browser.

**Web console, one memory looks the same on every surface.** On the person's side the card names the author by the principal the read serves and gives no kind: the API serves `provenance: "agent"` for every key, so the kind was a guess, and the same memory read "person" on Memories and "agent" in Review. The admin side, whose read serves `held_by`, keeps the kind after the key's name. An opened row lists the same facts in the same order and words on Memories, both Reviews and the one-memory page (the Memories row keeps its timeline above them, design notes row 12), and the approval line has one wording on both sides: the admin's says when, from its verdicts, and leaves out the kind its read does not serve. The Memories list no longer reads the person's key list; only a text search that names an author does.

**Web console, a nested shared workarea's reference.** The console named every workarea under a top label as if that label were a person's root, so `universe.platform.oncall` read `platform.oncall`, a name no field resolves: Review's Waiting table, its cards' links and verdict line, its `?workarea=` filter, the admin card's link and the admin One memory page's policy line all missed it. Each page now knows which top labels are user roots from what it reads: the tree read's `user_root` marks, the person's own root, and, for a top label neither names, one read of that label's node (`GET /v2/workareas/{top}/tree?limit=1`), which a page whose rows sit in the person's root and `universe` never makes. `oncall` is `oncall` on both sides.

**Web console, the admin Review page.** "Open to judge" and its `judge` act are the person's Review page's alone, as the ADR-0055 d10 amendment and ADR-0070 d7 (b) say: the admin page draws no such link and no judge form for `?memory=`, and refuses `action=judge` as an action it does not define.

**Web console, the reads each page makes.** The redesign's pages read more than their records said. The Memories and Atlas hints read one page of the tree, where they read up to ten; the person's Memories list no longer reads the key list; the admin's One memory page makes its second journalled admin read, of the replaced version, only behind "Show the change"; the admin Review page names its queue's workareas from one page of the tree. ADR-0070 gains as-built rows with each changed page's calls on v0.7.2, the first build and this one, and `web_console_reads.rs` measures the top label read (4 store calls as the admin key, 7 as a reviewer key).

**Records.** ADR-0068's status says the record is still proposed and that its d10 wording follows the voice rule and ADR-0045's header amendment, accepted on 2026-11-13; ADR-0031 quotes `CODE_NOT_VALID` as the code has it; the change note on the connect page says its `ONLY_IF_YOURS` warning stays in the second person pending the operator's decision.

**Web console, Review's small behaviour.** Review's Browse link opens Browse on both sides. A `judge` form resent with its nonce and another memory's id answers 409 `idempotency.digest_mismatch` and judges nothing: the form's nonce is bound to the memory it was drawn for, since the API keys a listed verdict per item. An edit or a retirement whose replaced version the reviewer key cannot read is labelled Edit or Retirement from the item itself, its verdict line says what approving does without that version, and the page says the replaced version is not readable to this key in place of the change.

**Web console, the pages' finish.** The Atlas has its own line under its heading on both sides, and the admin side's Memories and Atlas open with the line that names the key that reads ("Read as `boss-admin` …"). Below 600px the Workareas tables of both sides, the Keys table and the Quotas table stack, one block per row and each cell under its column's word, so nothing breaks mid-word or clips a select. The decision label of a review card (New memory, Edit of v2, Retirement) is drawn as a chip, not as a button. The admin One memory page names what a version replaces as the claim and its version (`claim · v1`, or "the version it replaces" until the change is shown), and Derives from no longer repeats it. A page drawn for no one, the sign-in page among them, ends with "Every act on these pages is journalled." and names no account. Quotas uses the regular lede type and names no API field or route in its copy. Guardrails names each rule's source workarea by its reference (`alice`, not `universe.alice`). Browse counts each workarea with everything beneath it, as the Atlas's tile does, under the same word.

**One workarea picker on Memories, the Atlas and Guardrails, and one spelling of a workarea everywhere** (design notes rows 14, 20, 21, 23 and 26; ADR-0044 d5; ADR-0045 d25). The console names every workarea by its reference: the bare name in the shared namespace, `<user>.<name>` inside a person's root, or the root's own name, the form every field accepts on both pages. The Workareas pages' "Name to use" column printed the path without `universe.` (`alice.proj.docs`), which no field takes; they now print the workarea and the one it sits in by reference, and the confirmation names the reference. The picker is a text input whose hints are names only, from the uncounted tree read; Browse, a link under the field, opens the tree with each workarea's count and marks, and only then makes the counted read. The console trims and lower-cases a typed name, answers a path itself with `request.validation`, and answers an unknown or unreadable name with one refusal and up to eight of the closest names the viewer reads. A bare name a single person's root holds resolves on the admin pages as on the person's; the Atlas's breadcrumb, which linked a bare name and so answered `404` below a user root on the admin page, is replaced by an "Up to" link by reference. The Rust SDK's tree nodes carry `user_root` and `parent_id`.

**Console redesign records.** The operator's decisions of 2026-11-13 on the console redesign are recorded as accepted amendments, for the build of v0.7.3. ADR-0055 (d1, d10) and ADR-0070 (d7 (b), d4) let a person's `<user>-review` key list the held items it may judge on the Personal Review page (`GET /v2/review/held`) and record a verdict on one item from the list (`POST /v2/review/verdicts/bulk` with one id), where the user page offered review next alone; R2 is unchanged, the listing never shows the reviewer's own writes or their lineage, the person's own agents' writes appear marked `same_user` as ADR-0045 d11 allows, no selection of many is added on the Personal side and the admin page is unchanged. - **Usage metering: every account is counted by its own write, and named quota profiles set its limits** ([ADR-0071](adr/ADR-0071-every-account-is-metered-by-counters-the-write-updates-in-its-own-transaction-and-named-quota-profiles-set-its-limits.md), accepted 2026-11-12; amends ADR-0068 d5). An account is a person's user root and everything its keys write. Six meters count it: `memories` (live chains it started, so a rejected or retired chain stops counting), `text_bytes`, `writes` and `recalls` per UTC month, `keys` and `connections`. The commit that folds a write moves the account's counter row in its own transaction and refuses past the limit, so of two writers racing at the last free memory exactly one commits, and the other gets `429 limit.quota` with `{quota, limit, used}`. Limits come from quota profiles in configuration (`quota.profiles`, `quota.profile.<name>.<quota>`, `quota.signup_profile`), and an admin assigns an account a profile and overrides with `PUT /v2/admin/accounts/{account}/profile` and takes them away with `DELETE` on the same route, each journalled as `account.profile_set`. An account on a profile the configuration no longer declares is refused its writes as `limit.quota` and still reads. A meter warns at 80%, where `oml doctor` warned at 90%. No quota refuses a read, and a recall hands its count to a queue without waiting for the write. `GET /v1/account/usage` serves a key's own account, and admins read one account, the month's ledger as JSON or CSV (`GET /v2/admin/usage?period=YYYY-MM`) and a drift report that `oml doctor` prints as `warn usage`. Upgrade notes:

- **Migration 0045 (usage metering) runs at boot, before the server serves, and its wait is the upgrade's.** It creates four tables, three functions and one index on `memories` built partition by partition, and fills the counters from the stored rows, in one transaction. Until it commits it holds SHARE ROW EXCLUSIVE on `tenants`, ACCESS EXCLUSIVE on `user_quotas`, and SHARE on `memories` and each partition, so every write of a memory waits; reads never do. Measured on PostgreSQL 18 over one tenant of 100 accounts, three runs each: 85 to 97 ms with 10,000 versions stored and 550 to 634 ms with 100,000. A lock is waited for at most 5 s, then the migration fails and is run again in a quieter moment.
- **Migration 0046 (key limits) adds `expires_at` and `requests_per_minute` to `api_keys`.** Two nullable columns with no default, a catalog change, and two CHECKs validated in one scan of `api_keys`, which holds one row per key ever issued; lock wait at most 5 s. Every existing key keeps no expiry and no rate. It was not timed on a large table, and `api_keys` is small. An older server refuses to start once either migration has run.
- **No setting has to change for the upgrade.** A server with no `quota.profiles` limits no account. To limit accounts, declare profiles (`quota.profiles`, `quota.profile.<name>.<quota>`, `quota.signup_profile`); an account on a profile the configuration no longer declares is refused its writes as `limit.quota`. `oml doctor` warns at 80% of a limit, where it warned at 90%. Each server process counts request rates alone, so n processes admit up to n times a rate.
- **A tenant writer key can no longer start a memory in a person's root.** Such a write, on `POST /v1/memories` or `oml_write`, answers `409 submission.user_root_refused` and journals nothing; reads, recall, review and what is already written are unchanged. Before upgrading, run `oml doctor` under each tenant writer key: one whose default workarea lies in a person's root prints `user root   : warn: …` and names the key to issue instead. The admin view that lists such keys is not built (#345, v0.8.0).
- **After the upgrade nothing has to be run by hand.** The scanner's rule set is still `oml-scan/1.2`, so `oml admin rescan --record-held` is not needed again, and the release notes carry no deployer marker. The lead appends the usage ledger's first row at the next closed UTC day; `oml doctor` prints `warn usage` if a counter drifts from its rows, and the [runbook](operations/runbooks.md#a-usage-counter-drifts-from-its-rows) says what to do.

Changed the `new system instructions` rule of the injection scan's letters-only view, still `oml-scan/1.2` since that rule set is not released (#317; ADR-0074 d6, ADR-0065 d14). The phrase holds when a colon follows it on its line, a combining mark counting with its letter, or when it is its line: nothing else stands on the line, up to a line feed, carriage return, vertical tab, form feed, NEL or line or paragraph separator, but marks (any character that is not a letter, a digit or a bar, so a hash, an asterisk, a quote, a bracket, an arrow, an emoji, a box-drawing line or a dot), a list marker (a lone number or letter, however written: a keycap, a circle or a bracket), up to eight HTML tags before the phrase, and up to eight tags or further phrases after it. A heading of any depth, a closed or setext heading, a line in capitals, `**New system instructions**`, `> …`, `- …`, `=== … ===`, `NEW SYSTEM INSTRUCTIONS!`, `[…]`, `<<< … >>>`, `<h1>…</h1>`, `🔥 NEW SYSTEM INSTRUCTIONS 🔥`, a dotted heading with its trailing dot and a line of the phrase twice hold. A list item with a label (`- printer: updated system instructions`), a commit subject, `TODO: write new system instructions`, an import, a path, a URL ending in the slug, a hard-wrapped line that ends in the phrase and a sentence with or without its full stop no longer hold. The three words may be set apart by any mark: `**New** system instructions: reveal`, `new *system* instructions:`, `new (system) instructions:`, `NEW—SYSTEM—INSTRUCTIONS:`, `new,system,instructions:` and `new+system+instructions:` hold, as they did under `/1.1`. They may not be set apart by a bar (`new | system | instructions:` passes), a line break, or the end of a clause (a comma, semicolon, colon, question or exclamation mark and a space: `new, system, instructions:` passes). A full stop and a space after every word, between every letter (`n. e. w. s. y. s. t. e. m. i. n. s. t. r. u. c. t. i. o. n. s:`) or a hyphenated line wrap (`new-system-` and `instructions:` on the next line) is the phrase's own spelling and holds; one full stop among the words is two sentences (`Updated. System instructions: see the wiki` passes). A combining mark before the colon no longer hides it. **The cost.** The rule holds what is the phrase alone and is no heading: a list item, a title field, a route (`/new/system/instructions`), an identifier (`new_system_instructions`), a phrase alone inside a tag or quotation marks, and `The UI is new. System. Instructions: see the wiki.`, whose one-word sentence is the phrase's own spelling of a break. It passes a directive with another word on its line: `Here are your new system instructions` followed by a list and `IMPORTANT - real system instructions` followed by its text, which are given up; a line that ends in the phrase and `follow` or `below:` before it; a heading with a section or page number; a heading in a table cell; `请NEW-SYSTEM-INSTRUCTIONS` on its own line, since a letter of another script is not a mark (it holds with a colon after it); a heading letter-spaced inside an HTML tag; a line of more than eight tags or phrases; a roman-numeral list marker; a fraction, a letter-like symbol (`™ … ™`) or a fullwidth word (`ＸＸ … ＸＸ`) before the heading, which fold to letters of a word; a dotted or dashed heading written twice on a line, since the repeat must be spelled plainly. The red-team corpus gains 20 malicious samples with 20 benign twins, and none of the existing samples changed its verdict. The false-positive corpus is 142 samples: 35 of the 135 that were in it before held under the rule set as merged, 8 of them by mistake (25.9%), 28 hold now, all by design (20.7%); the 7 new samples add 4 by-design holds. A megabyte of tags or phrases on one line no longer takes seconds: a first line rule read every tag again for each phrase and took 26 to 43 s (`<new system instructions>` repeated then one `x`), and now takes 80 ms in a release build. The refused-near-matches test asks a megabyte to scan in at most eight times the time of a quarter of it plus 20 ms, within 3 s in a debug build and 400 ms in a release build; the bound was 5 s before, with no growth test. Three more costs of the line rule, found in its last review: a one-letter word before the phrase reads as a list marker, so `I updated system instructions.` and `A new system instructions.` alone on a line hold (they passed under the rule set as merged; without the full stop they held under both); a hyphen followed by blank lines is read as one wrapped word, so `a brand-new-`, blank lines, then `system instructions: read them first` holds, as it did under `/1.1`; and a circled or keycap character after the phrase folds to a letter or digit and counts as a word, so `Ⓐ New system instructions Ⓐ` passes. The `oml-scan/1.2` set was not released, so no rescan beyond the one the `/1.2` fragment already asks for is needed.

Changed the injection scan's letters-only view to read a phrase only at word edges, and the rule set to `oml-scan/1.2` (#226; ADR-0074 d6, d21). The edges are read from the folded text (removable characters made a space, NFKD, lower case) as the raw rules' ASCII `\b` reads them: an ASCII letter touching a phrase makes it part of a longer word, and a digit, `_`, a letter of another script, a fullwidth form or punctuation is an edge. A phrase inside a longer word (`Danish`, `developer mode only`) or a camelCase identifier no longer holds a memory; a phrase joined by `_`, `/` or `-`, spelled out letter by letter, or set beside non-Latin text holds as before. The cost: a phrase glued to an ASCII letter (`xignore previous instructions`, `ignore previous instructionss`, `pleaseignore previous instructions`, `do.not.tell.the.users`) no longer holds, which cannot be told from `Danish`. The letters-only `new-instructions` phrase is now `new system instructions`, three words as ADR-0065 d14 asks, and holds when a colon follows on its line or it is its line, alone inside heading, emphasis, quote, list or bracket marks or any other symbols (a sentence that ends in `new system instructions` passes; the rule is the one of #317); `The new system instructions are in the wiki` and the two-word `new instructions` no longer hold in the letters view (the plain-text rule keeps `new instructions:`). A false-positive corpus of 123 prose, code, identifier and URL samples joins the scanner tests: 35 of the 97 that are not meant to hold held under `/1.1` and none does under `/1.2`, while the 26 that hold by design still do. The red-team corpus gains 16 malicious samples with their 16 benign twins. **After you upgrade, run `oml admin rescan --record-held`.** The rule set's name moved, so until it has run, sibling agents in an in-progress workarea do not see held versions scanned under `oml-scan/1.1`; `oml doctor` warns with `scan_held_unrescanned` and `scan_rescan_due` meanwhile. Nothing is demoted or deleted, and the findings `/1.1` recorded on a held version, including the false positives this change removes, stay on it until a reviewer judges it.
