# Release notes

Newest first. Each release is a signed tag on the [releases page](https://github.com/e8kor/open-memory-lab/releases).

## 0.8.5

Released 2026-11-26.

**v0.8.5 lets agents shape workspaces over MCP, gives people a key builder and key rotation in the console, and lands the first four pieces of ADR-0097.** `oml_write` writes guardrails, creates a child workspace inside its person's own root, and proposes a status move or a brief member that a different identity ratifies off MCP; the MCP server still serves three tools ([ADR-0095](adr/ADR-0095-an-agent-creates-its-own-child-workspaces-writes-guardrails-and-proposes-status-and-brief-changes-through-oml-write-and-every-verdict-and-setting-stays-with-people.md)). A seventh meter, `workspaces`, counts every workspace below an account's root. A person's web session builds a key with grants inside the person's root, a default workspace, a guardrail scope, an expiry and a rate; the administration console reads one key, sets its limits and denies it; the admin workspace page gains a Fix tab, the personal side lists imports, and To do gains brief proposals and admin fixes to confirm ([ADR-0096](adr/ADR-0096-a-person-builds-a-key-in-the-console-with-grants-inside-the-own-root-and-a-rate-and-the-admin-reads-one-key-and-sets-its-limits.md)). A bearer key rotates to a new value with an optional grace of up to 24 hours (d13), and an admin grants a person read on a workspace (**Grant read**). The CLI writes skills, and the SDKs keep a value a later server adds. From [ADR-0097](adr/ADR-0097-every-admin-act-is-one-journalled-record-narrowing-takes-effect-at-once-widening-waits-on-a-second-admin-person-and-every-admin-key-belongs-to-a-person.md), decided for v0.8.6, four pieces land: the read-only production counts, the deny's stored reason, the docs drift, and a last-admin guard that holds on every surface. Not built in this release: the console's workspace export page, which waits on the SDK's binary download ([#465](https://github.com/e8kor/open-memory-lab/issues/465)), and the review of an imported version on the console, which ADR-0096 d11 defers. The breaking changes and the upgrade come first below; the changes follow, grouped.

### Breaking changes

These change what an existing client gets, pre-release and without a shim (ADR-0039 d1).

- **The Python SDK upgrades with the server.** `my_effective_verbs` gains `create_workspace` and `propose_brief`, values the v0.8.4 Python SDK's generated model does not know: its workspace read raises `ValueError` on a v0.8.5 server wherever a key holds either. The v0.8.5 SDKs keep a value they do not know as its string, so this is the last upgrade in which an SDK moves in the server's window for new values alone. The TypeScript SDK already read them as strings.
- **`oml_write` gains three modes and kind `guardrail`** ([ADR-0095](adr/ADR-0095-an-agent-creates-its-own-child-workspaces-writes-guardrails-and-proposes-status-and-brief-changes-through-oml-write-and-every-verdict-and-setting-stays-with-people.md)): `create_workspace`, `propose_status` and `propose_brief`. Every tool annotation is unchanged, so a client permission rule that allows `oml_write` without a prompt now admits a create and both proposals without one too. A second live proposal to the same status, or of the same claim for the same brief, is `409 proposal.pending` on every transport, where a script that proposed twice got two proposals before.
- **The last admin entry of a tenant is kept on every surface** ([ADR-0097](adr/ADR-0097-every-admin-act-is-one-journalled-record-narrowing-takes-effect-at-once-widening-waits-on-a-second-admin-person-and-every-admin-key-belongs-to-a-person.md) d25, d27 item 4). `oml web allow` un-flagging it and `oml web remove` removing it are refused, `request.validation` naming `admin`, under a bearer admin key too, as the console already refused them; `keep_an_admin` is read and changes nothing. This reverses ADR-0045 d10's allowance for the CLI.
- **A rotated key's previous value, inside its grace, runs only the acts its deployment needs** (ADR-0096 d13). It still runs memory reads and writes, verdicts, edge proposals and ratifications, settling a fix, withdraw, uploads, imports into an existing workspace and export. It is refused every admin act and every act that creates a credential or changes structure or authority: issuing a key, a connect code, rotation, cut-off, denial, limits, linking and accepting a link, every session key act, creating a workspace (an import's new target included), its mode and federation, and status proposals and ratifications, each `access.verb_ceiling` with `details.reason: previous_value`.

### Upgrading

Past the limit a create is `429 limit.quota` and journals nothing.
- **Send the client notice on that page first, and upgrade the Python SDK with the server.** A client rule that allows `oml_write` without a prompt now admits a create and both proposals; to keep a prompt before them, put `oml_write` under an ask rule.
- **A proxy that routes `oml-web`'s paths by name adds four**: `/web/keys/new`, `/web/admin/fixes`, `/web/workspaces/import` and `/web/todo/fix`, as `deploy/caddy/Caddyfile`, both compose files and the chart's `web.ingressPaths` do.
- **Before the v0.8.6 upgrade, take the read-only counts** with `scripts/ops/read_only_counts.sh` on the database host, as the owner role with its password in `PGPASSFILE`; it changes nothing and prints `count,tenant,value`.
- **No rescan.** The scanner's rule set stays `oml-scan/1.3`, so the notes carry no deployer post-step.

### MCP workspace management

**Accepted: agents manage workspaces over MCP by proposal and own children.** [ADR-0095](adr/ADR-0095-an-agent-creates-its-own-child-workspaces-writes-guardrails-and-proposes-status-and-brief-changes-through-oml-write-and-every-verdict-and-setting-stays-with-people.md), accepted by the operator on 2026-11-24: `oml_write` gains the modes `create_workspace` (a contributor key creates a child inside its own person's root, immediately, with no grant written, under a new `workspaces` quota meter, 100 per account on the public server once its operator sets `OML_QUOTA__WORKSPACES`), `propose_status` and `propose_brief` (each ratified by a different identity on HTTP, the CLI or the console, one live proposal per target on every transport; a contributor key may propose a brief member and not a status move), and admits kind `guardrail` with a `guardrail` object, approved only by a person. `oml_workspace` stays read-only and the server serves three tools. Mode, crew, grants, keys, export, import, federation, claim edges, releases and every verdict stay off MCP. Connector keys get the modes, and no key creates a child in a shared workspace in v0.8.5. Decided then, and built in this release (below).

**Agents shape workspaces over MCP, and a guardrail is written on `oml_write`.** ADR-0095 is built. `oml_write` takes kind `guardrail` with a `guardrail` object, `{severity, rule?}`, the name as `claim_key`, approved only by a person's verdict, and supersedes a guardrail into kind `guardrail` with its object. Its `create_workspace` mode creates a child inside the person's own root from a contributor key that names that person, immediately and with no grant of its own; every other key is `access.verb_ceiling`, `details.reason: create_is_own_root_only`. `propose_status` (a reviewer key) and `propose_brief` (a contributor or reviewer key, on every transport) propose what a different identity ratifies off MCP. Two mode fields in one call are refused naming the second. `oml_workspace` stays read-only, the tool count stays three, and `my_effective_verbs` gains `create_workspace` and `propose_brief`. The server instructions gain one paragraph, at 3,071 characters, and the plugin skill a section, "Organise work into workspaces".

**The seventh meter, `workspaces`, and one live proposal per target.** Migration 0067 adds the `workspaces` meter: every workspace below an account's root, whoever made it, moved by the create's own commit and refused past the limit as `429 limit.quota`; the `default` profile leaves it unlimited, `quota.workspaces` sets it, and the drift report and the ledger carry it. On every transport a workspace holds one live proposal per target status and a claim one proposal per brief: a second is `409 proposal.pending`, naming `details.transition_id` or `details.edge_id` ([#515](https://github.com/e8kor/open-memory-lab/issues/515)). Pending transitions on the workspace read and pending brief edges on the brief's listing serve `proposed_at`, and `proposed_by: {id, name}` to a key of the proposer's person, null to every other (the amendment of 2026-11-24). The three create and proposal bodies take an optional `reason`, scanned and journalled. The upgrade note names the one permission effect: a client rule that allows `oml_write` without a prompt now admits a create and both proposals too.

**The console builds keys, reads one key for the admin, and adds the Fix tab, the import pages and the brief group.** ADR-0096 is built. ### Key rotation

**A bearer key rotates to a new value, with an optional grace.** [ADR-0096](adr/ADR-0096-a-person-builds-a-key-in-the-console-with-grants-inside-the-own-root-and-a-rate-and-the-admin-reads-one-key-and-sets-its-limits.md) d13 is built: `POST /v2/keys/{key}/rotate {grace_seconds?}`, `oml keys rotate` and **Rotate** on both Keys tabs give a bearer key a new value, shown once, and keep its name, grants, denials and limits, with an optional grace of up to 24 hours in which the previous value keeps working (migration 0069, `key.rotated`, `whoami`'s `rotation_grace_until` and doctor's `info key.rotation_grace_open`). The key rotates itself; a person rotates their own contributor, reader and submitter keys; an admin rotates its own admin key and a tenant key that names no person, and is refused another admin's key (`not_admins_key`) and a person's (`in_persons_root`) until ADR-0097's confirmation arrives in v0.8.6. Inside its grace a previous value still runs memory reads and writes, verdicts, edge proposals and ratifications, settling a fix, withdraw, uploads, imports into an existing workspace and export, so a deployed client keeps working while it moves to the new value. It is refused every admin act and every act that creates a credential or changes structure or authority: every key act, every admin verb, creating a workspace, its mode and federation, status proposals and ratifications, accepting a key link and every session key act, `access.verb_ceiling` with `details.reason: previous_value` and `details.verb`.

### CLI

**`oml write` writes skills, and `oml keys rotate` rotates a key.** `oml write --kind skill --skill-name <name> --skill-description <line>` writes a skill, and `oml write --help` lists `skill` and `document`. `oml keys rotate <key> [--grace <dur>] [--out <file>]` prints the new value once, or with `--out` writes it to a new owner-only file and prints none.

### SDK forward compatibility

**The SDKs keep what a later server adds.** The Python SDK keeps an enum value its spec does not list, such as a new verb or state, as its string instead of raising, and an error code it has never seen lands in its family's class, as the TypeScript SDK already did. Both SDKs gain `ProposalError` for the new `proposal` error family. The Rust SDK reads the review fixes and settles them, lists investigations, and lists a brief's edges.

### ADR-0097's pieces in v0.8.5

[ADR-0097](adr/ADR-0097-every-admin-act-is-one-journalled-record-narrowing-takes-effect-at-once-widening-waits-on-a-second-admin-person-and-every-admin-key-belongs-to-a-person.md), accepted design of 2026-11-25 and decided for v0.8.6, lands four pieces here (d27):

- **The read-only production counts.** `scripts/ops/read_only_counts.sh` runs one `READ ONLY` transaction as the database owner role, counts each tenant under its own `oml.tenant_id`, ends in `ROLLBACK`, and prints `count,tenant,value` for unlinked admin keys, service admin keys, grants in another person's root, admin-issued user keys and connect codes, open investigations and `admin_persons_ever`. It refuses a URL that carries a password.
- **The deny's reason** is scanned and journalled in `key.denied` when sent, completing ADR-0096 d4.
- **The docs drift is fixed**: key revocation and demotion are described as built where they are, and ADR-0045 d12's demote route carries a superseded note.
- **The last-admin guard is unconditional**: the tenant's last live admin entry is kept on every surface, the CLI's bearer admin key included, reversing ADR-0045 d10's allowance.

## 0.8.4

Released 2026-11-24.

**v0.8.4 is admin investigations and fixes, links and sign-in emails that wait on their person, the writer role split into contributor and submitter, withdraw as a mode of `oml_write`, and a LangChain integration in the Python SDK.** An admin reads claim text only under an open investigation that states its reason, and fixes a workspace at once by a marked break-glass act (demote, edit, retire or erase) that a person confirms or reverts afterwards: another person anywhere but the admin's own root, where a key of the admin's own person settles it, marked `same_user` ([ADR-0089](adr/ADR-0089-an-admin-fixes-a-production-workspace-at-once-by-a-marked-break-glass-act-that-a-person-confirms-or-reverts-afterwards.md)). A key an admin links to a person, and a sign-in email an admin adds for an existing person, take effect only once that person accepts them from their own console session ([ADR-0085](adr/ADR-0085-a-workspace-publishes-immutable-releases-that-one-person-cuts-and-another-ratifies-and-each-key-binds-to-the-tip-the-latest-release-or-a-pinned-one.md) d16, [ADR-0045](adr/ADR-0045-people-sign-in-to-a-user-page-and-an-admin-page-on-the-servers-own-origin.md)), and the bootstrap names the first admin's person and sign-in email (`--person`, `--email`). The role `writer` becomes `contributor`, a key that recalls and writes, and `submitter`, a key that writes without recall, with no alias ([ADR-0093](adr/ADR-0093-contributor-and-submitter-replace-writer.md)), so clients upgrade in the server's window and no key is issued or listed until both run v0.8.4. The MCP server serves three tools, `oml_write`, `oml_read` and `oml_workspace`: withdraw is `oml_write {withdraw}`, and `oml_withdraw` is gone ([ADR-0083](adr/ADR-0083-the-memories-page-is-one-cockpit-with-approved-to-review-and-submitted-views-and-held-rows-never-appear-as-approved.md) d13, amended 2026-11-24). The Python SDK's extra `langchain` adds a LangChain retriever, the `oml_write` and `oml_read` tools, and a LangGraph store that writes only inside an in-progress workspace ([ADR-0094](adr/ADR-0094-a-langchain-integration-rides-the-python-sdk-and-its-store-writes-only-into-an-in-progress-workspace.md)). Two dependency advisories are cleared by patch releases. A fix's release overlays wait for releases, which are designed and not built. The breaking changes and the upgrade come first below; the changes follow, grouped.

### Breaking changes

These change what an existing client gets, pre-release and without a shim (ADR-0039 d1).

- **Contributor and submitter replace writer, with no alias** ([ADR-0093](adr/ADR-0093-contributor-and-submitter-replace-writer.md)). `writer` is unknown input as a key role or a grant role on HTTP, MCP, the SDKs and the CLI: `request.validation`, with no `details.renamed_to`, since it has two successors. Migration 0066 makes every writer key a contributor key and every writer grant a submitter grant. Issuance refuses a contributor without a reader and a submitter grant (`details.reason: contributor_grants`). `oml keys issue-agent --write-only` is retired for `--role submitter`. A submitter recalls nothing and reads by id only the rows it wrote, and imports and the user-root workspace create admit a contributor key alone. Signed events keep `writer` and are read through the former-name map's rule 7. A v0.8.4 server refuses a v0.8.3 CLI, plugin or SDK that sends `writer`, and a v0.8.3 server refuses a v0.8.4 client that sends `contributor`, each issuing nothing, while recall and write work across the two: clients upgrade in the server's window, and no key is issued or listed until both run v0.8.4 (the operator's decision of 2026-11-24).
- **The admin reads take an open investigation.** `POST /v2/admin/memories/search` and `GET /v2/admin/memories/{id}` name an open investigation of their key (`investigation`, `?investigation=`), else they are refused `admin.investigation_required`; `oml admin investigate --reason` opens one and `oml admin read --investigation` names it.
- **A link an admin makes waits on its person.** `POST /v2/keys/{key}/link` answers `pending: true`, and the key acts for no one until the named person accepts it, `POST /v2/keys/{key}/accept_link`. Migration 0064 moves every link made before it to pending, except the bootstrap admin key's.
- **A sign-in email an admin adds for an existing person waits on that person.** It signs in to nothing, refused `auth.invalid` with `details.reason: email_pending`, until that person accepts it, `POST /v2/web/emails/accept` with `{email, admin}`.
- **The bootstrap claim with `person` requires `email`**, the person's sign-in address: `oml bootstrap claim --person <name> --email <address>`.
- **The MCP server serves three tools, and `oml_withdraw` is gone** ([ADR-0083](adr/ADR-0083-the-memories-page-is-one-cockpit-with-approved-to-review-and-submitted-views-and-held-rows-never-appear-as-approved.md) d13, amended 2026-11-24). Withdraw is `oml_write {withdraw: <artifact_id>, reason?, idempotency_key}`, with the same refusals and replay as before. A call to `oml_withdraw` is refused as an unknown tool (JSON-RPC -32602), with no alias, and `oml_write` with `artifact_id` is refused `request.validation` naming `/artifact_id`. A permission rule that names `oml_withdraw`, a deny or ask rule included, protects nothing after the upgrade, and a rule that allows `oml_write` without a prompt now lets withdraw through without one too. The HTTP route, `oml withdraw` and the console's Withdraw are unchanged.
- **A version an admin fix wrote names no author**: `principal` and `author_key_id` are null and `provenance` is `admin_fix`, a new value. Every served version carries `approver.act` (`verdict` or `admin_fix`) and `approver.confirmed`.

### Upgrading

[Upgrade OML](operations/upgrades.md#upgrading-to-v084) holds the steps and the client notice; read it before the window is announced. In short:

- **Clients upgrade in the server's window, and no key is issued or listed until both run v0.8.4.** Send the notice on that page first. Recall and write work across the two versions; key issuance and listings do not. Existing writer keys become contributor keys; reissue any that `oml doctor` names `key_contributor_without_recall` as a submitter key (`oml keys issue-agent <name> --role submitter`) and cut the old one off.
- **The upgrade is not rolling.** Back up and verify that the backup restores, since migration 0066 has no reverse. Stop `oml-web`, the lead and the lake writer, and start v0.8.4 of all three from one tag.
- **Migrations 0063, 0064 and 0066 run at boot, in that order**, after 0065, which a v0.8.3 database already holds. 0063 creates an empty table. 0064's link move and its two validating scans of `api_keys` hold key lookups until it commits, about 400 ms at 1,000,000 keys in the fourth review of #498. 0066 rewrites two small tables, a row per key and per grant.
- **Links and sign-in emails wait on their person.** Each person accepts their links (**Accept link**) and pending emails (**Accept sign-in email**) on their Keys page. An admin key takes a fix only once it is linked to its person and the link is accepted. `oml doctor` (admin key) warns `key.link_pending` and `web.email_pending` with their counts.
- **MCP clients drop `oml_withdraw`.** Scripts and agent prompts that name it move to `oml_write {withdraw}` in the server's window: a v0.8.3 server refuses the `withdraw` field. Permission rules that deny or ask on `oml_withdraw` move to `oml_write`, under an ask rule where a prompt before a withdrawal is wanted. Send the notice on that page with the role-rename notice.
- **No rescan.** The scanner's rule set stays `oml-scan/1.3`, so the notes carry no deployer post-step.
- **A stage or development database that ran a draft of 0063 or 0064 is reset**: the server refuses it with a checksum mismatch. Production at v0.8.3 never ran either.

### Admin investigations and fixes

**An admin reads claim text under one reason per investigation.** `POST /v2/admin/investigations {reason}` opens an investigation of the admin key, its reason stored in clear and scanned, journalled as `admin.investigation_opened`; `GET /v2/admin/investigations?state=open|closed` lists the key's own with their read counts and ages, and `POST /v2/admin/investigations/{id}/close` ends one, only by the key that opened it ([ADR-0089](adr/ADR-0089-an-admin-fixes-a-production-workspace-at-once-by-a-marked-break-glass-act-that-a-person-confirms-or-reverts-afterwards.md) d10, d15, d17; #423). Both admin reads, `POST /v2/admin/memories/search` and `GET /v2/admin/memories/{id}`, name an open investigation of their key (`investigation`, `?investigation=`), else they are refused with the new `admin.investigation_required` naming the field; each `memory.admin_read` names the investigation, and `oml_admin_reads_total` counts reads served. An investigation never expires: `oml doctor` warns `admin.investigation_open_long` for one open more than seven days. `oml admin investigate --reason|--close` and `oml admin read --investigation` are the CLI; the console asks for the reason the first time an admin page shows text, keeps the investigation in the browser session, and carries a **Close investigation** control. Migration 0063 adds `admin_investigations`.

**An admin fixes a workspace at once, and a person confirms or reverts the fix.** `POST /v2/admin/fixes {act, target, reason}` takes a marked break-glass `demote`, `edit`, `retire` or `erase` by an admin key used by a person (`admin.fix_requires_person` otherwise); one commit journals the lifecycle event it causes and `admin.fix` naming it, the reason stored in clear and scanned ([ADR-0089](adr/ADR-0089-an-admin-fixes-a-production-workspace-at-once-by-a-marked-break-glass-act-that-a-person-confirms-or-reverts-afterwards.md) d1-d4, d16, d17; #422). Every served version now carries `approver.act` (`verdict` or `admin_fix`) and `approver.confirmed`. `GET /v2/admin/fixes` lists the tenant's fixes; `GET /v2/review/fixes` lists the unconfirmed ones a person's reviewer key may see, with the acts it may take, and `POST /v2/review/fixes/{id}/confirm|revert` settles one: a revert serves the earlier text again as a new version authored by the tenant's reserved server key (`oml:server`, revoked at issuance) and approved by the reverter. A key of the admin's own person settles a fix only inside that person's own root and outside any release; anywhere else, open shared workspaces included, another person does (amendment of 2026-11-18; #490). New codes: `admin.fix_target_not_promoted`, `admin.fix_held_by_scan`, `admin.fix_superseded`, `admin.fix_not_revertible`, `admin.fix_settled`. `oml admin fix demote|edit|retire|erase`, `oml admin fixes` and `oml review fixes [--confirm|--revert]` are the CLI; `oml doctor` gains five `admin.fix_*` lines; metrics `oml_admin_fixes_total{act,loosens_guardrail}`, `oml_admin_fixes_unconfirmed` and `oml_admin_fix_oldest_unconfirmed_seconds`. Migration 0064 adds `admin_fixes` and the fix mark on `memories`. The Python and TypeScript SDKs raise `AdminError` for the `admin` family. Release overlays wait for releases.

**An admin fix takes an admin key linked to its person.** An admin key used by a person is linked to that person through the console's linking flow (never to the console admin's own person), and `oml bootstrap claim --person <name>` creates that person's user root and links the first admin key in the ceremony; a fix by an admin key that names no person answers `admin.fix_requires_person` with `details.reason: unlinked` ([ADR-0089](adr/ADR-0089-an-admin-fixes-a-production-workspace-at-once-by-a-marked-break-glass-act-that-a-person-confirms-or-reverts-afterwards.md), the operator's decision of 2026-11-19; ADR-0085 d16). A confirm or revert settles only when both persons are known and differ, outside the admin's own root; a revert, and a confirm of an edit or retirement, are refused `same_person` to a person who wrote the claim, read from the author's person recorded at each write. A version a fix wrote names no author to a reader (`principal` and `author_key_id` null, `provenance: admin_fix`); `approver.reverted` marks a version whose fix was reverted; the guardrail frame, MCP skill prompts and document resources name the fix and whether a person confirmed it. The serving role updates only the settlement and close columns of `admin_fixes` and `admin_investigations`, and a guard keeps each moving once.

**A user key counts as its issuer's person.** Where authority is weighed, an admin fix's person, who confirms or reverts a fix, and the author's person a write records, a user key counts as the person its issuer counts as: a key the person's own console session issued counts as that person, and one an admin or another person's key issued in someone's root counts as its issuer's person, or as no one. A key an admin linked to alice mints in carol's root therefore cannot confirm alice's fix of carol's claim (`same_person`). A settling key acts for the fix's admin's person on either reading too, so a key alice's admin key mints in bob's root settles bob's fix only as bob would, marked `same_user` in bob's own development root and refused `same_person` elsewhere, never as another person's confirmation; a key whose issuer chain counts it through the fix's admin key settles as that admin's person after a relink of that key too. A revert, and a confirm of an edit or retirement, read the settling key on both readings against the claim's lineage, so a key bob's admin key mints in dora's root reverts a fix of dora's claim marked `same_user`. `oml doctor`'s `admin.fix_admin_person_only` reads the settlement's own predicate, so a reviewer key that counts as no one is no other person who could confirm. Review's `same_user` mark and R2 by person read both the person a key counts as and the root it was issued in ([ADR-0089](adr/ADR-0089-an-admin-fixes-a-production-workspace-at-once-by-a-marked-break-glass-act-that-a-person-confirms-or-reverts-afterwards.md), the operator's decision of 2026-11-20).

**A demotion's reopened end is compare-and-set.** `lifecycle.demote` names the version a demotion reopens and the end it gives back (`reopened_artifact_id`, `restored_valid_until`); both stores now compare-and-set that pair with the demotion, as they do its restored tip, and refuse a stale one as a moved tip, so the signed event never names an end the store did not write ([ADR-0089](adr/ADR-0089-an-admin-fixes-a-production-workspace-at-once-by-a-marked-break-glass-act-that-a-person-confirms-or-reverts-afterwards.md) d16, note of 2026-11-18; #474).

**A claim whose approved versions are all demoted is written again, continuing its numbers.** Demoting a claim's last approved version releases its key: a new write continues its version numbers (v3 after v1 and v2), and the usage meter counts the chain as the one memory it was ([ADR-0089](adr/ADR-0089-an-admin-fixes-a-production-workspace-at-once-by-a-marked-break-glass-act-that-a-person-confirms-or-reverts-afterwards.md) d16, O8 of 2026-11-19; #474).

### Key links and sign-in emails

**A key's link to a person takes effect only once that person accepts it.** A console admin's `POST /v2/keys/{key}/link` now leaves the link pending (`pending: true`, `key.linked_person` with `accepted: false`): the key acts for no one, so it writes nothing into the person's root, an admin key takes no fix (`admin.fix_requires_person`, `unlinked`) and a reviewer key settles no fix (`same_person`), until the named person accepts it from their own console session with **Accept link** on the Keys page, `POST /v2/keys/{key}/accept_link`, journalled `key.link_accepted`; anyone else is refused `not_named_person` or `session_only` ([ADR-0085](adr/ADR-0085-a-workspace-publishes-immutable-releases-that-one-person-cuts-and-another-ratifies-and-each-key-binds-to-the-tip-the-latest-release-or-a-pinned-one.md) d16 and ADR-0089, the operator's decisions of 2026-11-19). `GET /v2/whoami` lists the person's `pending_links`, and `oml doctor` warns `key.link_pending`. The bootstrap's `--person` link is made by that person and is accepted at once. Each fix records its admin's person (`admin_person`), and the settlement compares that record, so a relink after the fix changes nothing. A fix whose mark a later fix takes over is settled `superseded` and leaves the person's list (ADR-0089 d17). An open investigation's read count never goes down. Migration 0064 adds `api_keys.link_pending_user_id`, `admin_fixes.admin_person` and `admin_fixes.superseded_by`.

**A key's link is set only through its person, in the database too.** Migration 0064's `api_keys_link_guard` admits a change of `api_keys.linked_user_id` only to NULL, from the pending link to the same root, or on the bootstrap ceremony's own admin key, and refuses any change of `issued_by`; 0064 moves links made before it, every key's but the bootstrap admin key's, to pending, so each person accepts them. A stage or development database that applied an earlier draft of 0064 is reset ([upgrades](operations/upgrades.md)).

**The database refuses an inserted key that carries a link.** 0064's `api_keys_link_guard` now covers inserts: a key is inserted with no link and no pending link, and the ceremony's own link is admitted only while its key is the tenant's only one (ADR-0085 d16).

**An admin can no longer quietly become a person who signs in already.** An email an admin adds with `POST /v2/web/emails` (the console's People page, `oml web allow`) for a person who has signed in before, or an entry changed to name such a person, is now pending (`pending: true` on the entry and on `web.email_allowed` / `web.email_changed`): it signs in to nothing, refused `auth.invalid` with `details.reason: email_pending` and no session, until that person accepts it from a session they already have, `POST /v2/web/emails/accept` (journalled `web.email_accepted`), the **Accept sign-in email** act on their Keys page. Another person's session, the adding admin's included, is refused `not_named_person`, a bearer key `session_only`, an entry that waits on no one `not_pending`. The person removes a pending email with `POST /v2/web/emails/decline` (**Remove**), an admin with `POST /v2/web/emails/remove`. A new person's first email signs in at once, as before. `GET /v2/whoami` serves the person's `pending_emails`; `oml doctor` warns `web.email_pending` (rescan report `web_emails_pending`). A pending admin entry keeps no admin for the last-admin rule ([ADR-0045](adr/ADR-0045-people-sign-in-to-a-user-page-and-an-admin-page-on-the-servers-own-origin.md), the operator's decision of 2026-11-19).

**A person a key names is an existing person, and the bootstrap claim records its person's email.** An address an admin adds for a user whose root a key names (a user key, a linked key or a pending link) now waits on that person, as one for a person who signed in does. `POST /v2/bootstrap/claim` with `person` now requires `email`, the person's sign-in address, which it records as the person's accepted admin entry; the ceremony commits as one chain, so a claim refused at the email, one another tenant holds, leaves no tenant and the token claims again; `oml bootstrap claim --person <name> --email <address>`, the quickstart script and the PoC demo send it. A change that would leave the tenant's last admin entry pending is refused as its un-flagging is. `GET /v2/whoami`'s `pending_emails` lists each address with its `admin` flag and the admin key that last set it, which the Keys page shows, and `POST /v2/web/emails/accept` takes `{email, admin}`: an entry whose flag changed since is refused `changed` ([ADR-0045](adr/ADR-0045-people-sign-in-to-a-user-page-and-an-admin-page-on-the-servers-own-origin.md), the operator's decisions of 2026-11-20).

### Contributor and submitter replace writer

**Contributor and submitter replace writer.** [ADR-0093](adr/ADR-0093-contributor-and-submitter-replace-writer.md), accepted on 2026-11-19, renames the grant role `writer` to `submitter` and splits the key role into `contributor`, a key that recalls and writes with at least one reader and one submitter grant, and `submitter`, a key that writes and reads only its own rows. Existing writer keys become contributor keys, and `oml doctor` names any without a reader grant, to be reissued as a submitter key; no act changes a key's role. Imports, the user-root workspace create and the console's issue form take contributors only. Signed events keep `writer` and are read through the former-name map of [ADR-0091](adr/ADR-0091-workareas-become-workspaces-and-the-dreamer-role-becomes-reviewer-on-every-surface-in-one-cut-and-the-journals-former-names-are-read-through-one-map.md). `writer` becomes unknown input on every surface and `--write-only` is retired. Decided then, and built in this release (below).

**Contributor and submitter replace writer, built.** [ADR-0093](adr/ADR-0093-contributor-and-submitter-replace-writer.md) ships: a key that recalls and writes is a `contributor`, a key that writes without recall is a `submitter`, and the grant role that confers writing is `submitter`. Issuance refuses a contributor without a reader or a submitter grant with `request.validation`, `details.reason: contributor_grants`, and never adds a grant. Migration 0066 rewrites stored writer keys to contributor and writer grants to submitter under each tenant's row security, and signed events are read through rule 7 of the former-name map, so a rebuilt database equals the migrated one. Uploads admit contributor and submitter keys; imports and the user-root workspace create admit a contributor key alone; the curator's ceiling reads `submitter`; a submitter reads by id only the rows it wrote, recalls nothing, and is issued no `universe` reader grant. `writer` is unknown input on every surface and `oml keys issue-agent --write-only` is retired for `--role submitter`. A contributor key with a submitter grant on a node no reader grant of it reaches is a contributor without recall: `whoami` and `GET /v2/keys` serve it as `without_recall`, a session key the server holds for a person never, `oml doctor` names it (`key_contributor_without_recall`) and the console marks it "no recall"; the console's issue form offers `contributor` and `reader`. The vocabulary lint covers `writer` as a role, in docs prose and shell scripts too. Clients upgrade in the server's window, and no key is issued or listed until both run v0.8.4 ([upgrades](operations/upgrades.md)).

### Skills, documents and test cases

**Skills, documents and test cases are claim kinds, and a held version can be withdrawn.** `POST /v1/memories` and supersession take `kind: skill` with `skill {name, description}`, `kind: document` with an optional `document {title}`, and `kind: test` with `test {shape}`. Each object is signed with the version, stored beside it and served on every read of it. A skill is `text/markdown`, which a request that names no format gets by default, at most 32,768 bytes, with no front matter. Its claim key is derived as `skill/<name>`, and a successor keeps the name. A document's key is `doc/` and plain segments, sent or derived from its title by the heading slug rule (a long title keeps 47 characters and a digest), and the title defaults to the first level-1 heading, cut to 200 characters. A test case's key is `test/<name>`. Each field outside its grammar is refused `request.validation` naming it. The kinds follow their classes (a skill is an instruction, a document and a test case are knowledge). They are written over the HTTP API only: `oml_write` refuses them until their serving lands. Migrations 0048 and 0049 add the four columns, the `withdrawn` state and the `document_passages` table, adding their checks `NOT VALID` and validating them outside a transaction. A withdrawn version releases its claim key and has no live search postings. The listings and the admin search take `state: withdrawn` ([ADR-0080](adr/ADR-0080-a-skill-is-a-reviewed-claim-the-mcp-server-lists-as-a-prompt-and-serves-as-a-resource-loaded-live-and-never-copied.md) d1, d2, d9, d10, d16; [ADR-0081](adr/ADR-0081-a-document-is-a-reviewed-markdown-or-text-claim-that-recall-searches-by-passage-and-the-mcp-server-serves-as-a-resource.md) d1, d2; [ADR-0086](adr/ADR-0086-a-workspaces-tests-are-reviewed-claims-the-server-runs-under-the-callers-key-and-a-release-is-published-only-through-ordered-gates.md) d1; [ADR-0083](adr/ADR-0083-the-memories-page-is-one-cockpit-with-approved-to-review-and-submitted-views-and-held-rows-never-appear-as-approved.md) d13; #400).

**Skills are offered as MCP prompts and resources.** A skill is written by any writer, over `oml_write` with `kind: "skill"` and its `skill` object or over `POST /v1/memories`, and every version waits for a person's approval. `GET /v1/skills` serves the skills offered at the key's scope, 50 a page with a set digest and no bodies: the scope node's own, its readable ancestors' under `guardrail_scope: ancestors`, and inside an in-progress workspace the subtree below it, the nearer workspace winning a shared name and naming what it `overrides`. The key's own held skills and an in-progress workspace's held skills are offered marked `unreviewed`, a held edit of an approved skill, and a held skill whose name another offered workspace holds approved, as `<name>-unreviewed`, at most 50 held at once. The MCP server lists the guardrails prompt and then each offered skill on `prompts/list`, answers `prompts/get` with a header naming the workspace, version and approval, then the body and the input, and serves each skill at `oml://workspace/<workspace>/skill/<name>` through `resources/list`, `resources/read` and `resources/templates/list`; any name or URI not offered answers one error. `oml skills list` prints the set, the session-start hook adds an index of up to 20 skills, the tool-call hook asks before a file is written under `.claude/skills/`, and `oml doctor` names a server without skills, a shadowed name and skills kept on disk ([ADR-0080](adr/ADR-0080-a-skill-is-a-reviewed-claim-the-mcp-server-lists-as-a-prompt-and-serves-as-a-resource-loaded-live-and-never-copied.md) d1 to d15, with the build's readings of 2026-11-17 and 2026-11-18; #403, #404, #408). The store-call timing series `instruction_rows` is now labelled by kind, `instruction_rows.guardrail` and `instruction_rows.skill`; a dashboard on the old label reads neither. The ask before a local skill write is checked on Windows by the CLI's unit tests with drive paths, mixed separators and a `USERPROFILE` home; the earlier note in commit b52eac1b that integration tests covered the Windows leg was wrong, since that leg runs the CLI's unit tests alone.

**Documents: one passage rule, `oml sync --adapter document`, and the passage cap.** A new leaf crate, `oml-passage`, holds the passage rule of [ADR-0081](adr/ADR-0081-a-document-is-a-reviewed-markdown-or-text-claim-that-recall-searches-by-passage-and-the-mcp-server-serves-as-a-resource.md) d3 with no I/O. It covers headings of level 1 to 4, sections over 40 lines cut at blank lines, and front matter and HTML comments skipped. The server and `oml-cli` both link it, and a shared vector file holds them to one cut. A heading's slug reads a link by its text on both sides, so a document titled `[Guide](https://x.y)` keys as `doc/guide` (ADR-0081 d2, amended). A document whose text cuts into more than 4,096 passages is refused with `request.validation`, `details.field: /body`, `details.reason: too_many_passages`. `oml sync --adapter document` writes one `document` claim per `.md` or `.txt` file, keyed `doc/` and the path without its extension, and anchored to the whole file. A path whose key falls outside the document key grammar is reported unreadable, and so is a file that cuts past the 4,096-passage cap, in a dry run as in a run. A run over a source that another adapter loaded is refused, naming both adapters and the claims it would leave (ADR-0081 d7). The build's readings R1 to R6 are recorded in ADR-0081 for the operator's batch (#405, #406).

**Documents are recalled by passage and served as MCP resources.** Each passage of a document is a search unit of its own: migration 0059 gives `document_passages` its search text, lexemes, length and served bytes, gives `search_postings` a passage `ordinal`, and has the fold write and count a document's postings one passage at a time. Every pipeline reads a document through its passages, and a version that is not a document is one unit, ranked as before. A `bm25-postings` recall over a scope with no readable document runs the statement that reads no passage, so its cost on such a scope stays that of the statement before documents. A recall serves a document once, as its best passage: the hit's text and tokens are the passage's, and it carries `passage` (fragment, ordinal, lines and headings), `more_passages` (a lower bound) and `uri`, `oml://workspace/<workspace>/doc/<path>?passage=<fragment>`. A recall without `kinds` includes documents, and `kinds` admits `document`. `oml_write` takes `kind: document` with its `document` object. The MCP server lists documents in `resources/list` before the skills, reads one whole or by passage in `resources/read`, and serves the document URI template. Document versions written before 0059 have their passages cut when the lead starts. `oml doctor` warns of a server that predates documents, a path loaded both as a document and by another adapter, and a document file past the passage cap (ADR-0081 d1 to d6, d8, d9; readings R7 to R9) (#405).

**The SDKs read the skill set and write skills and documents.** The Python and TypeScript SDKs read the skills offered at a workspace one page at a time, `skills` (`GET /v1/skills`, with `workspace`, `include_own_held` and `cursor`), and every page in turn, `iter_skills` in Python and `iterSkills` in TypeScript, which follow `next_cursor` until it is null. Their `write` takes `skill` (`name` and `description`) and `document` (`title`), on a new claim and on a supersession alike. The Rust SDK, `oml-sdk`, gains `Client::skills`, a recall's `kinds` (`RecallQuery::kinds`; none named sends no `kinds`, so the server's default applies, ADR-0092 d1) and a document hit's `passage`, `more_passages` and `uri`. Withdraw was already in all three (#401). Helpers for releases and bindings wait for them to be built ([ADR-0080](adr/ADR-0080-a-skill-is-a-reviewed-claim-the-mcp-server-lists-as-a-prompt-and-serves-as-a-resource-loaded-live-and-never-copied.md) d11; [ADR-0081](adr/ADR-0081-a-document-is-a-reviewed-markdown-or-text-claim-that-recall-searches-by-passage-and-the-mcp-server-serves-as-a-resource.md) d1, d4; #427).

### Search over every kind, and the catalog

**Search finds every kind of claim, and a read without a query is the catalog.** Recall's `kinds` takes every kind but `test`, which is never a hit and is refused by name. A recall that names none ranks memories, derived facts, documents, the skills the scope offers and the guardrails that apply there in one list, each hit marked with its kind; a skill hit names its prompt and resource and serves its description, never its body, and a guardrail hit shows a rule already in force without binding anything. `kinds` decides whether the steering list is served (`steering: "not_requested"` otherwise), and `search.matched_by_kind` counts each kind's candidates before the `k` cut. `oml_read` without a query, `GET /v1/memories` without `own` and `oml read` without `--query` now answer the catalog: every kind the key reads, filtered by `kinds`, `prefix` and `state`, entries without text unless `include_text`, and per-kind counts on the first page, capped by the new `catalog.count_cap` (10,000). On MCP `own` now defaults to `false`: an agent asks for its own work with `own: true`. Migration 0062 gives every hit kind search postings, tests none, and adds the catalog's index; it refills each tenant holding a skill, guardrail or vocabulary row, measured at about 225 s per million versions of that tenant, and migration 0061 now commits each tenant's backfill alone ([ADR-0092](adr/ADR-0092-search-filters-by-every-claim-kind-and-ranks-skills-and-guardrails-as-data-and-a-read-without-a-query-is-the-catalog-of-what-a-key-reads.md), amended 2026-11-18 with the build's readings; #443).

### Review, approval and withdraw

**Only a person approves an instruction.** An approval of a `steering` or `guardrail` version counts only from a person's reviewer key: `used_by: person`, with no crew and no profile. Any other key's approval is refused `review.person_required` with `details.reason: instruction_needs_person`, nothing is journalled, and the version stays held. A reject from the same key is still admitted, and a crew's agent key still approves knowledge and vocabulary. A promotion's recorded `policy` now names the version's `class` and `human_required`. The held listing marks each instruction `needs_person`, the review page shows "Needs a person" on the row and on the judge page, and `oml doctor` warns a reviewer key that is not a person's that its approval of an instruction is refused. Steering and guardrails promoted earlier on an agent's verdict stay promoted ([ADR-0080](adr/ADR-0080-a-skill-is-a-reviewed-claim-the-mcp-server-lists-as-a-prompt-and-serves-as-a-resource-loaded-live-and-never-copied.md) d3, d16; [ADR-0001](adr/ADR-0001-the-constitution.md) d5; #391).

**Instructions are served only to people.** The instruction class now has ADR-0074 d19's person lane. `review next` never serves a steering, guardrail or skill version, or a successor of another kind that replaces one, to a reviewer key that cannot approve it, so a crew is never handed an item it can only reject. `needs: person` serves only the lane, round-robin across author keys, each author's oldest first (the operator, 2026-11-17). The held listing takes `needs` and counts each author's items in the lane. The console's review list shows the lane first. ADR-0074's status line and ADR-0080 d16 record the decision of 2026-11-15; d19's cap, referral, dismissal and evasion parts stay proposed under #214 ([ADR-0074](adr/ADR-0074-the-scan-names-a-threat-class-for-every-finding-refuses-only-what-can-never-be-safe-holds-or-annotates-the-rest-and-recall-serves-every-hit-as-data-with-its-findings.md) d19; [ADR-0080](adr/ADR-0080-a-skill-is-a-reviewed-claim-the-mcp-server-lists-as-a-prompt-and-serves-as-a-resource-loaded-live-and-never-copied.md) d16; #437).

**Outside a person's own root, no key of that person judges what another of their keys wrote.** When the reviewing key and the version's author key act for the same person, a user key, a session key or a tenant key an admin linked to them, the verdict counts only inside that person's root, marked `same_user`. Elsewhere, approve and reject are refused `review.author_in_lineage` with `details.reason: same_person`, and review next and the held listing leave the row out for that key. A tenant key no admin linked acts for no person and is judged by key and principal as before ([ADR-0001](adr/ADR-0001-the-constitution.md) d5; [ADR-0082](adr/ADR-0082-a-person-builds-and-edits-a-workspaces-skills-guardrails-and-documents-in-the-console-each-edit-a-held-version-under-the-persons-own-keys.md) d7; #392).

**A version records its author's person at its write.** Since migration 0061 every version records, when it is written, the person its author key acts for (`memories.author_person`): a session key's person, the user root a user key names or a linked tenant key is linked to, or none. The `same_user` mark on an approval, R2 by person (the verdict refused outside the person's root, and the row left off that person's review listing and queue) and a person's session withdrawal read that record, so an admin unlinking a key between a write and its verdict no longer clears the mark or lifts the refusal. The migration gives every earlier version the person its author key resolves to when it runs ([ADR-0085](adr/ADR-0085-a-workspace-publishes-immutable-releases-that-one-person-cuts-and-another-ratifies-and-each-key-binds-to-the-tip-the-latest-release-or-a-pinned-one.md) d16, amended 2026-11-18; #448).

**The in-progress audience reaches the ancestors.** A read scoped at a workspace now serves every in-progress subtree below it as well as the one it sits in: recall and the scoped listing at a parent serve the subtree's approved rows as approved and its held rows, every author's, marked unreviewed, and `include_unreviewed` defaults to `true` whenever the served workspaces hold an in-progress subtree; the key's own held rows elsewhere in the scope need an explicit `true`, and `false` narrows every list, held steering included, to approved rows. A held version of every kind is served that way in the listing and by id, never a retirement and never one the scan held or has not scanned under the current rule set; recall's hits stay the knowledge kinds. A read at a sibling or on another branch, federation and wide sources still serve nothing of the subtree until its commit ([ADR-0080](adr/ADR-0080-a-skill-is-a-reviewed-claim-the-mcp-server-lists-as-a-prompt-and-serves-as-a-resource-loaded-live-and-never-copied.md) d16, amending ADR-0030 d2, d3, d4; #402).

**Held guardrails and steering reach their author and in-progress workspaces.** `GET /v1/guardrails` takes `include_own_held`, which the plugin's hooks and the MCP `guardrails` prompt send, and serves the key's own held guardrails as rules; on a node inside a workspace a person put in progress it serves every author's held guardrail too. Each held version is a line of its own after the approved rules, marked `unreviewed: true` with a null `promoted_at` and `effect_inside: "ask"`; the hook caches it with that effect, so an unreviewed rule asks and never denies, and the session text and the prompt prefix it `[unreviewed]`. The cap of twelve counts approved rules alone, so held versions never hide one, and at most fifty held versions are served beside them. Held steering and held guardrails reach the calling key alone, never another key of its person. An approved rule a held edit would replace stays in force with its own effect, and a held retirement or a version the scan held is never served. Recall's steering list carries held steering after the approved rows on the same terms, marked held, and the session-start text prefixes it `[unreviewed]` ([ADR-0080](adr/ADR-0080-a-skill-is-a-reviewed-claim-the-mcp-server-lists-as-a-prompt-and-serves-as-a-resource-loaded-live-and-never-copied.md) d10, d14, d16, amending ADR-0037 d3; #407).

**Withdraw.** The author of a held version now withdraws it: its own key, an agent's included, over `POST /v1/memories/{artifact_id}/withdraw`, the MCP tool `oml_withdraw` and `oml withdraw <artifact_id>`, and a person from the console's Memories page, on a held row any of their keys wrote, after a confirmation. **Demotion and erasure, the admin fix's two acts.** A demotion stops serving any approved version and keeps its bytes. When the version was the tip, the latest earlier approved version that is not demoted is served again. An as-of read skips a demoted version at every instant and serves the version below it; the journal still records what was served ([ADR-0059](adr/ADR-0059-a-memory-states-when-it-is-true-recall-hides-what-has-ended-and-searches-the-dates-a-query-names-without-a-model.md) d22). An erasure takes every version of a claim. In one transaction it empties each version's text and the search rows derived from it, erases its search telemetry and destroys its lake data key, and keeps the digest, the title, a skill's name and description, and the attribution. PostgreSQL's copies in backups last until the backup window ends ([ADR-0005](adr/ADR-0005-erasure-by-crypto-shredding.md) d2, d4). Migration 0056 lets the server destroy a data key without reading one. Migration 0057 adds a trigger so no role re-keys a destroyed key, moves a destruction's time, or writes a new key into a live row without a new key-encryption key. A demotion gives the version its ratification ended back the end it had before the supersession, whether or not the demoted version was the tip, and names it in `lifecycle.demote` (migration 0058). A retirement or a vocabulary term is not demoted (`lifecycle.demote_kind_unsupported`). `oml doctor` warns of held versions that no verdict can approve because their target is no longer the approved tip, and of erased versions whose data key is still live.

### Uploads, export and import

**The workspace bundle format is built (#425, #426).** A new leaf crate, `oml-bundle`, builds

- verification that fails closed with d7's codes;
- erasure markers that carry no digest;
- per-bundle pseudonyms;
- the d8 import plan as a pure function.

ADR-0084 records the operator's decision of 2026-11-17 that only the exporter's own versions carry
their signed source event, and nine readings the record left open. The readings cover the
container, order, manifest and line fields, `bundle.malformed`, `bundle.decrypt_failed`, markers,

**Upload sessions.** Bytes reach the server through resumable upload sessions ([ADR-0004](adr/ADR-0004-bodies-and-attachments.md) d3, amended 2026-11-17, #451). `POST /v2/uploads` opens a session with the declared size and SHA-256, `PUT /v2/uploads/{id}/parts/{n}` stores fixed 8 MiB parts that a retry sends again, `GET /v2/uploads/{id}` says which parts are missing, `POST /v2/uploads/{id}/complete` checks the digest, and `DELETE /v2/uploads/{id}` abandons the session. Parts are stored as XChaCha20-Poly1305 ciphertext under a key per session at `storage.url`, a local directory by default, and the key is nulled when the session expires, is abandoned or its consumer ends; [ADR-0005](adr/ADR-0005-erasure-by-crypto-shredding.md)'s inventory gains the row "upload staging". One upload is at most 1 GiB (`uploads.max_bytes`), a key holds at most 4 unbound sessions and a tenant at most 4 GiB of them (`uploads.tenant_max_bytes`); an open session lives 24 hours after its last part and at most 72, and an unbound completed one 24 hours. Only the key that opened a session sees it, and nothing about an upload is journalled. Ten `upload.*` codes name every refusal, and `oml doctor` gains an `uploads` line.

**Export.** A person exports a workspace's subtree as a signed `oml-bundle/1` encrypted to named age recipients ([ADR-0084](adr/ADR-0084-a-workspace-moves-between-servers-as-a-signed-bundle-that-lands-held-or-in-progress-and-is-reviewed-again-unless-its-source-server-is-pinned.md) d1-d5, d10, d13; #425). `POST /v2/workspaces/{workspace}/exports {mode, recipients}` answers the age file, and `oml workspaces export <workspace> --recipient <age1…> --out <file>` writes it to a new owner-only file. `history` mode, the default in a person's own root, carries every version ever promoted and the exporter's own held, rejected, demoted and withdrawn versions, never another key's; an erased version travels as a marker with no digest; only the exporting key's own writes carry their signed events. The manifest is signed by the journal key, whose fingerprint is the source server id. `release` mode and `since` are refused `request.validation` (`releases_unbuilt`) until releases are built. Only a key used by a person exports: an agent, admin or service key is `access.verb_ceiling` (`export_person_only`). No recipient is `bundle.unencrypted`, the tenant's policy refuses with the new `export.disabled`, and an unreadable node of the subtree with `export.not_readable`. Migration 0054 adds `tenants.export_policy` (default `own_root`), `export_allowances` and the `exports` meter; the routes that set the policy and an allowance come later. Each export is journalled as `workspace.exported`, counted by `oml_exports_total`, and named under `exports` by `oml doctor`.

**Import.** A person's writer key imports a workspace bundle into an in-progress workspace ([ADR-0084](adr/ADR-0084-a-workspace-moves-between-servers-as-a-signed-bundle-that-lands-held-or-in-progress-and-is-reviewed-again-unless-its-source-server-is-pinned.md) d6-d11, d15, #426). `oml workspaces import <file> --into <workspace> --identity <file>` decrypts the bundle on the importer's machine twice, verifies it, and sends it as the parts of one upload session; nothing decrypted is written to disk. `POST /v2/imports` verifies the bundle again, plans it against the target, and with `dry_run` answers the plan; otherwise it binds the upload, writes each new or changed claim key held by the importer with its source provenance, reports the bundle's edges (a claim edge whose two ends the target carries is proposed by the importer where its key may propose one, which a writer key may not), journals `workspace.imported`, and nulls the upload's key. `GET /v2/imports/{id}` answers the state, counts and refusals. A target that is not in progress is `import.target_not_in_progress`; a new name is created in progress. The first import from a source names `--expect-key` and pins it, and a later bundle under another key is `import.source_key_changed`; an older bundle is `import.bundle_older` unless `--allow-older`. Re-importing the same bundle writes nothing. Twenty new codes (`bundle.*`, `import.*`), the metrics `oml_import_refusals_total` and `oml_import_versions_total`, and an `imports` line in `oml doctor`. Migration 0055 adds `imports`, `import_ledger`, `import_versions` and `memories.import_provenance`. Not in this release: rollback (the admin fixes of ADR-0089, designed and not built), the same-server copy (`--from`), durable erasure notices, the To do list of imported versions with its attestation, and the equivalence of differing digests by format diff.

### Scanner, sign-in and quotas

**The scan vetoes an age identity.** The rule set is now `oml-scan/1.3`: a write that holds an age X25519 identity (`AGE-SECRET-KEY-1` and 58 bech32 characters), the secret half of a bundle recipient, is refused with `submission.scan_veto`, finding `secret.private_key: age-identity`, in either case and whatever word it is glued to on either side, when its bech32 checksum holds. Changed the `new system instructions` rule of the injection scan's letters-only view, still `oml-scan/1.2` since that rule set is not released (#317; ADR-0074 d6, ADR-0065 d14). The phrase holds when a colon follows it on its line, a combining mark counting with its letter, or when it is its line: nothing else stands on the line, up to a line feed, carriage return, vertical tab, form feed, NEL or line or paragraph separator, but marks (any character that is not a letter, a digit or a bar, so a hash, an asterisk, a quote, a bracket, an arrow, an emoji, a box-drawing line or a dot), a list marker (a lone number or letter, however written: a keycap, a circle or a bracket), up to eight HTML tags before the phrase, and up to eight tags or further phrases after it. A heading of any depth, a closed or setext heading, a line in capitals, `**New system instructions**`, `> …`, `- …`, `=== … ===`, `NEW SYSTEM INSTRUCTIONS!`, `[…]`, `<<< … >>>`, `<h1>…</h1>`, `🔥 NEW SYSTEM INSTRUCTIONS 🔥`, a dotted heading with its trailing dot and a line of the phrase twice hold. A list item with a label (`- printer: updated system instructions`), a commit subject, `TODO: write new system instructions`, an import, a path, a URL ending in the slug, a hard-wrapped line that ends in the phrase and a sentence with or without its full stop no longer hold. The three words may be set apart by any mark: `**New** system instructions: reveal`, `new *system* instructions:`, `new (system) instructions:`, `NEW—SYSTEM—INSTRUCTIONS:`, `new,system,instructions:` and `new+system+instructions:` hold, as they did under `/1.1`. They may not be set apart by a bar (`new | system | instructions:` passes), a line break, or the end of a clause (a comma, semicolon, colon, question or exclamation mark and a space: `new, system, instructions:` passes). A full stop and a space after every word, between every letter (`n. e. w. s. y. s. t. e. m. i. n. s. t. r. u. c. t. i. o. n. s:`) or a hyphenated line wrap (`new-system-` and `instructions:` on the next line) is the phrase's own spelling and holds; one full stop among the words is two sentences (`Updated. System instructions: see the wiki` passes). A combining mark before the colon no longer hides it. **The cost.** The rule holds what is the phrase alone and is no heading: a list item, a title field, a route (`/new/system/instructions`), an identifier (`new_system_instructions`), a phrase alone inside a tag or quotation marks, and `The UI is new. System. Instructions: see the wiki.`, whose one-word sentence is the phrase's own spelling of a break. It passes a directive with another word on its line: `Here are your new system instructions` followed by a list and `IMPORTANT - real system instructions` followed by its text, which are given up; a line that ends in the phrase and `follow` or `below:` before it; a heading with a section or page number; a heading in a table cell; `请NEW-SYSTEM-INSTRUCTIONS` on its own line, since a letter of another script is not a mark (it holds with a colon after it); a heading letter-spaced inside an HTML tag; a line of more than eight tags or phrases; a roman-numeral list marker; a fraction, a letter-like symbol (`™ … ™`) or a fullwidth word (`ＸＸ … ＸＸ`) before the heading, which fold to letters of a word; a dotted or dashed heading written twice on a line, since the repeat must be spelled plainly. The red-team corpus gains 20 malicious samples with 20 benign twins, and none of the existing samples changed its verdict. The false-positive corpus is 142 samples: 35 of the 135 that were in it before held under the rule set as merged, 8 of them by mistake (25.9%), 28 hold now, all by design (20.7%); the 7 new samples add 4 by-design holds. A megabyte of tags or phrases on one line no longer takes seconds: a first line rule read every tag again for each phrase and took 26 to 43 s (`<new system instructions>` repeated then one `x`), and now takes 80 ms in a release build. The refused-near-matches test asks a megabyte to scan in at most eight times the time of a quarter of it plus 20 ms, within 3 s in a debug build and 400 ms in a release build; the bound was 5 s before, with no growth test. Three more costs of the line rule, found in its last review: a one-letter word before the phrase reads as a list marker, so `I updated system instructions.` and `A new system instructions.` alone on a line hold (they passed under the rule set as merged; without the full stop they held under both); a hyphen followed by blank lines is read as one wrapped word, so `a brand-new-`, blank lines, then `system instructions: read them first` holds, as it did under `/1.1`; and a circled or keycap character after the phrase folds to a letter or digit and counts as a word, so `Ⓐ New system instructions Ⓐ` passes. The `oml-scan/1.2` set was not released, so no rescan beyond the one the `/1.2` fragment already asks for is needed.

Changed the injection scan's letters-only view to read a phrase only at word edges, and the rule set to `oml-scan/1.2` (#226; ADR-0074 d6, d21).
