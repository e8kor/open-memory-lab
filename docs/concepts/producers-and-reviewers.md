# Producers and reviewers

Every write has a producer and needs a reviewer who is not that producer. Three pairs occur: an agent writes and a person approves; an agent writes and another agent's key approves; a person writes and another person approves. Which of them counts depends on the claim's class and on the scope: loose in development, strict toward production ([workspace lifecycle](../architecture/lifecycle.md)).

## How the check works today

- **A verdict needs a `reviewer` key.** Every other role is refused. A key `used_by: service` is refused every review verb, whatever its grants. An admin key never gives a verdict.
- **R2 is checked per key and per principal.** A verdict is refused `review.author_in_lineage` when the reviewer's key id or principal is anywhere in the version's lineage closure, its author included (`crates/oml-domain/src/model.rs`, `check_reviewer`). The recorded policy is one verdict, role `reviewer`, independence axis `principal`, no person required.
- **R2 is also checked per person, outside the person's own root.** When the reviewing key and the version's author key act for the same person, read as `same_user` reads it (a key's user root, the person a tenant key is linked to, or its console session), the verdict counts only inside that person's own root, where it is marked `same_user: true`. Anywhere else, approve and reject are refused `review.author_in_lineage` with `details.reason: same_person`, and review next and the held listing leave the row out for that key ([ADR-0001](../adr/ADR-0001-the-constitution.md) d5 and [ADR-0082](../adr/ADR-0082-a-person-builds-and-edits-a-workspaces-skills-guardrails-and-documents-in-the-console-each-edit-a-held-version-under-the-persons-own-keys.md) d7). A tenant key no admin linked acts for no person, so two such keys of one person with different principals still count as two reviewers.
- **The console counts as a person.** `<user>-review`, created at first sign-in, is a `reviewer` key `used_by: person` with reviewer and reader on the person's root. Console writes and console-issued agent keys each have their key name as principal, so the person's review key approves them, marked `same_user`.
- **No verdict travels over MCP.** An agent with a reviewer key judges over HTTP, `/v2` ([reviewer crews](../api/reviewer-crews.md)). An agent's own key never promotes or signs (R1); a reviewer crew's verdict is a review act by a different key.

## Who may approve what

|---|---|---|---|---|---|---|
| Knowledge: `memory`, `derived_fact` | agent key A | another person's reviewer key, `used_by: person` (the built check: another key and principal) | yes | yes | `approver.used_by: person` | built |
| Knowledge | agent key A of person P | P's review key, inside P's own root | yes | not applicable: the root stays `development` ([ADR-0085](../adr/ADR-0085-a-workspace-publishes-immutable-releases-that-one-person-cuts-and-another-ratifies-and-each-key-binds-to-the-tip-the-latest-release-or-a-pinned-one.md) d17) | `same_user: true` | built |
| Any class | a key of person P: a user key, a session key or a tenant key linked to P | a key of P, outside P's root | no (ADR-0082 d7: approve and reject refused `review.author_in_lineage` with `details.reason: same_person`; the row is neither listed nor served to that key) | no | none | built |
| Knowledge | agent key A | agent key B: a reviewer crew's reviewer key, `used_by: agent`, over HTTP, neither the author nor a key of the author's person | yes | yes: knowledge may be approved by a crew (ADR-0001 d5) | `approver.used_by: agent` | built |
| Knowledge | person A | person B | yes | yes | `used_by: person` | built |
| Knowledge: `document`, `test` | as `memory` | as `memory` | as `memory` | as `memory` | as `memory` | stored and reviewed as kinds over the HTTP API and `oml_write`; a document is recalled by passage and served as an MCP resource, and the suite is designed (#419) ([ADR-0081](../adr/ADR-0081-a-document-is-a-reviewed-markdown-or-text-claim-that-recall-searches-by-passage-and-the-mcp-server-serves-as-a-resource.md), [ADR-0086](../adr/ADR-0086-a-workspaces-tests-are-reviewed-claims-the-server-runs-under-the-callers-key-and-a-release-is-published-only-through-ordered-gates.md)) |

| Instruction: `skill` | agent key A or a person | a person, as above | as above | as above | as above | stored and reviewed as a kind over the HTTP API, a person's verdict required; offered as an MCP prompt and resource and listed by `GET /v1/skills` ([ADR-0080](../adr/ADR-0080-a-skill-is-a-reviewed-claim-the-mcp-server-lists-as-a-prompt-and-serves-as-a-resource-loaded-live-and-never-copied.md)) |
| Vocabulary: `term`, `term_mapping`, `vocab_release` | a writer key, over HTTP only | as knowledge, an agent's key included | yes | yes | as knowledge | built |
| Any class | any key | the author's key, or any key sharing a principal with the lineage | no | no | none | built: refused `review.author_in_lineage` |
| Any class, in progress | any key | an agent `curator` profile | never approves; rejects, proposes retirements, flags contradictions | not applicable | none | built |

"A person" in this table is, for now, a reviewer key its issuer attested `used_by: person`, with no crew and no profile. The stricter definition of [ADR-0074](../adr/ADR-0074-the-scan-names-a-threat-class-for-every-finding-refuses-only-what-can-never-be-safe-holds-or-annotates-the-rest-and-recall-serves-every-hit-as-data-with-its-findings.md) d2, a confirmed sign-in session opened within the last 15 minutes, is designed and comes with #214.

The person lane (ADR-0074 d19, accepted for the instruction class by ADR-0080 d16) is built: `review next` never serves a held steering, guardrail or skill version, or a successor of another kind that replaces one, to a key that cannot approve it. `needs: person` serves the lane alone, round-robin across author keys and each author's oldest first. The held listing counts the lane per author key, and the console's To do marks each such row "needs a person". Designed, not built: two `oml doctor` lines under an admin key, `instructions_unreviewable` (a workspace holding instructions that no person's reviewer key may approve) and `instruction_approvals` (instructions in force that a key other than a person's approved before v0.8.3).

Two more acts follow the same split, both designed: a release is cut in a shared workspace, by one person, and published by another person, since production rules govern a published release; no release is cut in a user root, which stays in development (ADR-0085 d4, d17); an admin fix is confirmed by the admin's own person under development rules, marked `same_user`, and only by another person under production rules or on a release's overlay ([ADR-0089](../adr/ADR-0089-an-admin-fixes-a-production-workspace-at-once-by-a-marked-break-glass-act-that-a-person-confirms-or-reverts-afterwards.md) d8).

## Who sees what where

The matrix says who may approve. The two Euler views below say who sees what. Each workspace is a region nested in its parent; a key's reach is the outlined region over them. A hollow circle is a held item, served marked unreviewed; a solid circle is promoted or published; a dotted, struck circle is held and not served to that key.
