Measured migration 0044's fill and made `oml doctor` count the promoted versions it could not fill (#311; ADR-0077 d6). On a loaded shared host under PostgreSQL 18 the fill took 0.84 to 1.5 s at 10,000 promoted rows and 13.4 to 21.6 s at 100,000, and `memories` grew about 70% until vacuum; the upgrade page now says so and ADR-0077 d6 cites the figures where it said "unmeasured". `GET /v2/admin/rescan` gains `promoted_unapproved`, the count of served versions (promoted tips) whose `approved_at` is null, read by an admin key from the pass that already counts the scan backlog, a count and never a list; `oml doctor` prints it as `approval_unmatched` and warns above zero, naming the remedy (supersede the version: once a reviewer approves the successor the count falls by one; or leave it). No command lists which versions they are. The OpenAPI schema and both SDKs carry the new member. An admin key whose read of the count fails is told so, `warn approval_unmatched: not read (<reason>)`, and a count that is not an unsigned integer is named, never read as zero.
