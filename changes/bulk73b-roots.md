**A memory is started in a user's root by that user's keys only** ([ADR-0044](adr/ADR-0044-every-user-works-under-a-root-of-their-own-and-universe-serves-curated-claims-without-their-source.md) d16, a **proposed** amendment the operator has yet to accept; #329). A tenant writer key holding a subtree grant on `universe`, or any grant inside a user's root, could start claims in `universe.<user>`; with usage metering that moved a person's `memories` with no check against their ceiling. A new memory there by a key that is not that user's is now refused `409 submission.user_root_refused`, on `POST /v1/memories` and on `oml_write`, and journals nothing. A reviewer granted there, a tenant key or another person's review key, still proposes a successor or a retirement of a served memory, as the admin page does; the one successor refused from it is that of a ratified retirement, which would put the claim back in service and on the user's `memories`. A person's session keys are their keys: `<user>-review` and `<user>-curate` carry no `user` and name their person by their session, and the rule reads a key's person the one way `same_user` does, so a person's review key puts a retired memory of theirs back, on the admin memory page as well, and is still refused in a root an admin only designated it to review. The code is answered only where the key reads the workarea or the target; a key that reads neither keeps `access.not_found`. Reads, recall and review there are unchanged, and nothing already written is touched: versions tenant keys wrote there before stay served, reviewable and under the accounting [ADR-0071](adr/ADR-0071-every-account-is-metered-by-counters-the-write-updates-in-its-own-transaction-and-named-quota-profiles-set-its-limits.md) d3 states, whose sentence now says no new write produces that case. The strict rule, every claim write from the user's keys only, was built first and rejected by the operator on 2026-11-12. `oml doctor` under a tenant writer key whose default workarea lies in a user's root warns and names the key to issue instead. Grants are unchanged, so `my_effective_verbs` still lists `remember` and `learn` for such a key. A user's own keys can still put a retired claim back past their `memories` limit (#340). [errors](api/errors.md), `openapi.yaml`, [roles and keys](architecture/roles-and-keys.md) and [workareas](architecture/workareas.md) carry the rule, and both SDKs' generated layers the new code.
