**Upload sessions.** Bytes reach the server through resumable upload sessions ([ADR-0004](adr/ADR-0004-bodies-and-attachments.md) d3, amended 2026-11-17, #451). `POST /v2/uploads` opens a session with the declared size and SHA-256, `PUT /v2/uploads/{id}/parts/{n}` stores fixed 8 MiB parts that a retry sends again, `GET /v2/uploads/{id}` says which parts are missing, `POST /v2/uploads/{id}/complete` checks the digest, and `DELETE /v2/uploads/{id}` abandons the session. Parts are stored as XChaCha20-Poly1305 ciphertext under a key per session at `storage.url`, a local directory by default, and the key is nulled when the session expires, is abandoned or its consumer ends; [ADR-0005](adr/ADR-0005-erasure-by-crypto-shredding.md)'s inventory gains the row "upload staging". One upload is at most 1 GiB (`uploads.max_bytes`), a key holds at most 4 unbound sessions and a tenant at most 4 GiB of them (`uploads.tenant_max_bytes`); an open session lives 24 hours after its last part and at most 72, and an unbound completed one 24 hours. Only the key that opened a session sees it, and nothing about an upload is journalled. Ten `upload.*` codes name every refusal, and `oml doctor` gains an `uploads` line.

**Export.** A person exports a workspace's subtree as a signed `oml-bundle/1` encrypted to named age recipients ([ADR-0084](adr/ADR-0084-a-workspace-moves-between-servers-as-a-signed-bundle-that-lands-held-or-in-progress-and-is-reviewed-again-unless-its-source-server-is-pinned.md) d1-d5, d10, d13; #425). `POST /v2/workspaces/{workspace}/exports {mode, recipients}` answers the age file, and `oml workspaces export <workspace> --recipient <age1…> --out <file>` writes it to a new owner-only file. `history` mode, the default in a person's own root, carries every version ever promoted and the exporter's own held, rejected, demoted and withdrawn versions, never another key's; an erased version travels as a marker with no digest; only the exporting key's own writes carry their signed events. The manifest is signed by the journal key, whose fingerprint is the source server id. `release` mode and `since` are refused `request.validation` (`releases_unbuilt`) until releases are built. Only a key used by a person exports: an agent, admin or service key is `access.verb_ceiling` (`export_person_only`). No recipient is `bundle.unencrypted`, the tenant's policy refuses with the new `export.disabled`, and an unreadable node of the subtree with `export.not_readable`. Migration 0054 adds `tenants.export_policy` (default `own_root`), `export_allowances` and the `exports` meter; the routes that set the policy and an allowance come later. Each export is journalled as `workspace.exported`, counted by `oml_exports_total`, and named under `exports` by `oml doctor`.

**Import.** A person's writer key imports a workspace bundle into an in-progress workspace ([ADR-0084](adr/ADR-0084-a-workspace-moves-between-servers-as-a-signed-bundle-that-lands-held-or-in-progress-and-is-reviewed-again-unless-its-source-server-is-pinned.md) d6-d11, d15, #426). `oml workspaces import <file> --into <workspace> --identity <file>` decrypts the bundle on the importer's machine twice, verifies it, and sends it as the parts of one upload session; nothing decrypted is written to disk. `POST /v2/imports` verifies the bundle again, plans it against the target, and with `dry_run` answers the plan; otherwise it binds the upload, writes each new or changed claim key held by the importer with its source provenance, reports the bundle's edges (a claim edge whose two ends the target carries is proposed by the importer where its key may propose one, which a writer key may not), journals `workspace.imported`, and nulls the upload's key. `GET /v2/imports/{id}` answers the state, counts and refusals. A target that is not in progress is `import.target_not_in_progress`; a new name is created in progress. The first import from a source names `--expect-key` and pins it, and a later bundle under another key is `import.source_key_changed`; an older bundle is `import.bundle_older` unless `--allow-older`. Re-importing the same bundle writes nothing. Twenty new codes (`bundle.*`, `import.*`), the metrics `oml_import_refusals_total` and `oml_import_versions_total`, and an `imports` line in `oml doctor`. Migration 0055 adds `imports`, `import_ledger`, `import_versions` and `memories.import_provenance`. Not in this release: rollback (v0.8.3's admin fixes), the same-server copy (`--from`), durable erasure notices, the To do list of imported versions with its attestation, and the equivalence of differing digests by format diff.

**Fixes of the bulk B review (2026-11-18).** The coordinator's readings of 2026-11-18 are recorded as ADR-0084 I10-I19, ADR-0004 d3's readings of 2026-11-18 and an amendment to ADR-0030 d1, each for the operator's batch. `POST /v2/imports` now answers `202` with the import `running` and runs it after the answer; a dry run still answers `200` with the plan, and `GET /v2/imports/{id}` answers the end. An import running for more than an hour that the lead is not running is ended `failed` by the upload sweep, which nulls its upload's key and removes its parts; a bound upload whose key is still set a day after binding is the doctor warning `upload_staging_stale`, and a failed shred is logged as `import_shred_failed`. The source key is pinned in the transaction that begins an import, so two first imports at once pin one key and a failed first import still pins its key; the end of an import never moves the pin. A tenant runs one import or dry run at a time and the server two, refusing `import.busy` (409, retryable); a tenant runs one export at a time, refusing `export.busy`. Each imported version's `import_provenance` and `import_versions` row is written in the version's own commit, `workspace.imported` lists the versions it wrote, and the doctor warns `imports_unprovenanced`. Reading an upload back recomputes its SHA-256 and refuses `upload.digest_mismatch`; binding requires the upload unexpired at that instant; a conflict over a removed key writes a retirement; a new import target is created in progress in one commit, and a retry against the importing key's own empty standard workspace marks it. The local object store writes through a fresh, exclusively opened temporary name, syncs the directory after the rename and keeps its root owner-only. The export readings of [ADR-0084](adr/ADR-0084-a-workspace-moves-between-servers-as-a-signed-bundle-that-lands-held-or-in-progress-and-is-reviewed-again-unless-its-source-server-is-pinned.md) dated 2026-11-18, built. A verdict on an erased version no longer travels, and the bundle reader refuses a verdict that names an erasure marker or a version the bundle does not carry, `bundle.malformed` (I17); a version's `derives_from` keeps only the ids the bundle exports whole. A key that belongs to a crew never exports: `access.verb_ceiling`, `export_person_only` (I18). A person's key exports every version its person's keys wrote, a bearer key its person's console writes included (I6 as written). A bundle larger than `uploads.max_bytes` is `export.too_large` before anything is journalled or metered, and a second export of one tenant while one runs is `export.busy` (I13); the limits page names both bounds, the import's, and the in-memory build, the whole-chain walk and the unbuilt per-day limit as bottlenecks. `oml_export_refusals_total` counts the route's refusals by code, and `oml doctor` names them under `exports`. Every export is counted on the tenant's new `exports` meter, `tenant_activity` in migration 0054, kept 62 days, so an export by a key with no account root is counted too (I19). `oml workspaces import` reads a running import every 2 seconds until it ends (I10), gives each request that moves the bundle 10 minutes, abandons the upload session it opened on every failure before the import takes it, prints a dry run's upload for `--upload <id>` to import without sending the bundle again, refuses a first import into a name that does not exist yet without `--expect-key` before uploading, warns when the identity file is readable by its group or others, and wipes the identity from memory after use. The TypeScript SDK's import error class is `WorkspaceImportError`, as the Python SDK's is. A tenant key linked to a person exports as itself alone, never with the person's other keys' unpromoted rows; an export whose stored body bytes already pass `uploads.max_bytes` is refused before any body is read, and the server runs two exports at most. Follow-ups: the console import hand-off and status page (#468), the To do list of imported versions (#469), durable erasure notices (#470), the same-server copy `--from` (#471), rollback (#472) and equivalence by format diff (#473).

**The server starts without its upload directory.** The directory `storage.url` names is opened on the first upload, not at start, so one the server cannot create (a relative default under a read-only working directory, as in a container or a systemd unit) no longer stops it. The server logs `upload_store_unavailable` once with the reason, serves every other route, and answers each upload, and each import that reads one, `upload.storage_failed` (503) until the directory can be created; each sweep tries again. The metrics listener serves `oml_upload_store_unavailable{reason}`, the reason a closed kind such as `permission_denied` or `read_only`, and `oml doctor` warns `upload_store_unavailable: object store unavailable: <reason>`. The release image sets `OML_STORAGE__URL=/var/lib/oml/objects`, a directory its user owns; the Compose file mounts the `oml-objects` volume there and the Helm chart an `emptyDir` (`objects.sizeLimit`, empty by default). A production install sets `storage.url` to an absolute directory the server can write before using uploads ([upgrades](operations/upgrades.md); [ADR-0004](adr/ADR-0004-bodies-and-attachments.md) d3, note of 2026-11-18).

**The lead never changes the mode of an upload directory it does not own.** A `storage.url` root the lead owns is tightened to owner-only as before; one owned by another user is never chmodded, and is refused, naming the owner and the mode, when its group or others can write it. The Helm chart therefore sets `storage.url` to `/var/lib/oml/objects/store`, which the lead creates below its volume, and `scripts/check_chart.py` refuses a storage URL that is not strictly below a mounted volume. The chart's objects emptyDir now defaults to `sizeLimit: 8Gi`, and `objects.persistence` mounts a ReadWriteOnce claim instead, off by default. A part the store lost before completion, as after a pod was replaced, is named by `upload.incomplete`, so the client sends it again. `scripts/quickstart.sh` opens, fills and completes a three-byte upload, so the chart and Compose jobs prove the lead writes its upload directory ([ADR-0004](adr/ADR-0004-bodies-and-attachments.md) d3, second note of 2026-11-18).
