**Sign-in.** The two provider points ADR-0045 d4 left unverified are checked against each provider's documentation, fetched and quoted on 2026-11-13, with the code that relies on each cited by file and line ([ADR-0045](adr/ADR-0045-people-sign-in-to-a-user-page-and-an-admin-page-on-the-servers-own-origin.md#the-two-provider-points-as-checked-against-the-providers-documentation-2026-11-13-119), #119). Google's ID token, received straight from its token endpoint over TLS with the client secret, may be accepted without a signature check (OpenID Connect Core §3.1.3.7 item 6, and Google's own guide), and the lead's issuer, audience, expiry, nonce and verified-email checks meet the conditions both set. GitHub documents the PKCE verifier as required once a challenge is sent, accepts S256 only and speaks of PKCE enforcement, but states no refusal of a wrong verifier; on GitHub PKCE is the only control against a code taken from another person's callback, so a live sign-in with a wrong verifier remains part of #119. The security page gains that threat's row. No code changes.
