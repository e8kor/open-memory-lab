**Web console and API.** A person sets an expiry on a key they issue themselves (#352; ADR-0079 d1, d5 and the operator's answer 3, built on the operator's word of 2026-11-12). `POST /v2/keys` as a person's `<user>-web` session key admits `expiry` under the rule of every issuance, an RFC 3339 instant with its offset, later than the server's clock, and still refuses `requests_per_minute` as `request.validation` naming the member. The Keys page's two issue forms, for an agent key and for a connector key, each carry one optional date input, **Key expires (optional; end of that day, UTC)**, which works without script; the page sends the day as its last second in UTC (`YYYY-MM-DDT23:59:59Z`), and a day that has passed or a value that is not `YYYY-MM-DD` is refused on the page as the API refuses the instant, with its status, code and message; a day its month does not hold, such as `2026-11-31`, is read as the day that many days on, as every `date-time` of the API reads it. Changing or clearing the date afterwards stays with the admin key role: a person's session key is still `access.verb_ceiling` on `POST /v2/keys/{key}/limits`, and the page says "only an admin can change it later". The Start page's one-button issue sets no date. Before, a person's own issuance refused `expiry` by name, so only an admin could date a person's key. The Rust SDK's `issue_key` takes the optional instant; no operation was added, and the CLI is unchanged. The pages were not looked at in a browser.
