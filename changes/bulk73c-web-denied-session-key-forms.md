**Web console and API.** A person whose `<user>-web` key carries a denial on any workarea is told so on the Keys page and the Start page, and neither draws the forms for the three acts that key is refused for good (#343; ADR-0070 d2, an amendment the operator accepted on 2026-11-12). The Keys page draws no **Issue key**, **Issue connector key**, **New connect code** or **Cut off**; the Start page draws no **Issue my credential**; each shows one sentence in their place: this session is refused issuing a key, minting a connect code and cutting off a key because its key carries a denial; an administrator can issue, connect and cut off keys for the person, and exporting their memories, requesting deletion and signing out still work. Before, the pages drew the forms and each answered the 403 `access.verb_ceiling`, `session_key_denied`, every time; `GET /v2/keys` shows `cut_off: false` for such a key when the denial is not on the whole root, so nothing the page read told it. The page now reads one served field: `GET /v2/whoami` carries `denied` on a session key's record, true when the key holds a denial on any workarea. It is absent on every other key, so an agent's key still learns nothing of its denials (ADR-0039 d15). The field comes from the access the session gate already read, so no read gained a store call: the five calls the two pages make cost 2, 2, 12, 4 and 8 store calls before the field and the same after it, with and without a denial on the key, and the `web_console_reads` suite is unchanged. The page test holds the page equal to the API's answer: each act sent anyway is the 403 the page drew no form for. `openapi.yaml`'s `Whoami` and both generated SDKs carry the field; no operation was added. The pages were not looked at in a browser.
