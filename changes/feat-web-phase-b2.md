- **`oml-web` ships and starts everywhere the server does** ([ADR-0070](adr/ADR-0070-the-web-console-is-a-client-of-the-public-http-api-in-a-crate-that-cannot-reach-the-application-core.md) d4, d6; issue #189). Each release attaches `oml-web-X.Y.Z-<target>.tar.gz` for the two server targets, with its SBOM, summed and signed like the server's, and the image carries `/usr/local/bin/oml-web` beside the lead. `docker-compose.yml` and `oml quickstart` start the lead, `oml-web` and a Caddy router, the one published port, which sends each page `oml-web` serves to it and every other path to the lead; quickstart's `.env` now holds the web client secret both read. The Helm chart gains `oml-web`'s Deployment, Service, ServiceAccount and NetworkPolicy and a web client Secret the chart creates once and reads back on every upgrade. An Ingress routes by path alone and cannot match the one page `oml-web` serves today, `GET /web?view=guardrails`, so the chart routes no path to it by default (`web.ingressPaths`). The server serves `GET /web/sign-in`: `oml-web` sends a person with no session there with the page as `next`, which the server keeps only as a path under `/web` with no `//`, `\`, `@` or scheme, checked again after one more percent-decoding, and returns to on its configured origin after sign-in. `oml-web` answers `/readyz` on its own listener, ready while the server is ready and accepts its secret, and `oml-web --doctor` prints `web.api_url` as `ok`, `warn` or `fail` and whether the server is ready. `deploy/caddy/Caddyfile` is the production route table. `RELEASE-HOLD` is gone, so a tag releases again. Upgrading a deployment means starting `oml-web` beside the server with the same `web.client_secret` and adding its route to the proxy ([Run the web console](operations/web-console.md)).
