- **Usage metering: every account is counted by its own write, and named quota profiles set its limits** ([ADR-0070](adr/ADR-0070-every-account-is-metered-by-counters-the-write-updates-in-its-own-transaction-and-named-quota-profiles-set-its-limits.md), proposed; amends ADR-0068 d5). An account is a person's user root and everything its keys write. Six meters count it: `memories` (live chains it started, so a rejected or retired chain stops counting), `text_bytes`, `writes` and `recalls` per UTC month, `keys` and `connections`. The commit that folds a write moves the account's counter row in its own transaction and refuses past the limit, so of two writers racing at the last free memory exactly one commits, and the other gets `429 limit.quota` with `{quota, limit, used}`. Limits come from quota profiles in configuration (`quota.profiles`, `quota.profile.<name>.<quota>`, `quota.signup_profile`), and an admin assigns an account a profile and overrides with `PUT /v2/admin/accounts/{account}/profile`, journalled as `account.profile_set`. A meter warns at 80%. No quota refuses a read. `GET /v1/account/usage` serves a key's own account, and admins read one account, the month's ledger as JSON or CSV (`GET /v2/admin/usage?period=YYYY-MM`) and a drift report that `oml doctor` prints as `warn usage`. The lead appends one ledger row per account per closed UTC day, kept 25 months, and logs `usage_rollup`. `/web/start`, the person's page and `/web/admin/users` show the meters. The counts never hold text or a query. Migration 0038 adds the tables and fills them from the stored rows.
