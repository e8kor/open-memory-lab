Added a page, [when a recall repeats](architecture/repeatable-recall.md), and the test behind it (#176): under the default pipeline, `bm25-postings`, the same recall returns the same steering, hits, order and scores byte for byte, call after call and from a second server process over the same database. `recall_id` always differs; `timings` and `search.widen` can differ where served. The page lists the inputs that define an answer (the request, the key, the approved set, `now`, the settings and the server version), what changes it between calls, and what is outside it: `timings`, the `search.widen` hint, the pipelines that read a model, and a recall with `as_of`, which the test does not cover (the `bm25` scan reads each `bm25-postings` list and each `sparse` list, so `bm25-sparse`, `bm25-sparse-rrf` and `bm25-postings-time`, which fuse those lists, are swapped too, and `keyword-any` with every word required answers `keyword-all`). A held write leaves every other key's answer unchanged; its approval changes the answer once. The test ran on 14 approved memories, serial plans, PostgreSQL 18.6 locally and 17 in CI. The last digit of a score, and the order of two hits one `float4` step apart, is not proven identical across query plans, PostgreSQL versions or parallel worker order; it is not observed and not excluded, and #310 tracks proving it.
