- **A web console act claims its `Idempotency-Key` before it acts, so two sends of one form act once** ([ADR-0070](adr/ADR-0070-the-web-console-is-a-client-of-the-public-http-api-in-a-crate-that-cannot-reach-the-application-core.md) d3 layer 4, d5; issue #233; migration 0042). The acts `oml-web` runs through the API (issuing a key, minting a connect code, cutting a key off, creating a workarea, proposing, ratifying, setting a mode, granting capacities, the quota, disable, deletion request and close) recorded their outcome after they committed. A double click that reached the API twice, as it can through two `oml-web` replicas, acted twice: the second issue of a key answered `name.taken` and its value was never shown. Each act now claims its key in a transaction of its own first. A second send waits up to 5 s and replays the first's outcome, so the key's value or connect code is in the first answer only and never stored. The act and its record run in a task of their own, so a request dropped mid-act, as `oml-web`'s call timeout drops one, still records the outcome and the resubmission replays it. Only an act refused before anything committed frees its key. An act whose outcome cannot be recorded after it committed, or whose step after the commit fails, keeps its claim, so a resubmission answers `409 idempotency.in_progress` and repeats nothing; the lead logs `idempotency_unsettled`, counts `oml_idempotency_unsettled_total`, and `oml doctor` warns. The runbook lists the claims held and how old each is. Migration 0042 grants the serving role `UPDATE` of `response` and `committed_at`, and `DELETE`, on `idempotency`; it takes `ACCESS SHARE` and `SHARE UPDATE EXCLUSIVE` on that table, which wait on no read or write.
