**Web console and API.** A session key an admin denied no longer issues a key (#325; ADR-0070 d2, d8, a proposed amendment). `POST /v2/keys` as `<user>-web`, `POST /v2/keys/{key}/connect-codes` and `POST /v2/keys/{key}/denials` as a session key read the key's access when they run and refuse one that carries a denial, on any workarea, with `access.verb_ceiling`, `details.reason: session_key_denied`, journalling nothing. Before, a `<user>-web` key denied on `universe` still issued a key holding the person's whole root with no denial on it. The refusal is permanent and any denial brings it, one on a workarea outside the person's root included: no verb lifts a denial, and removing the person's address and adding it back leaves the same `<user>-web`; from then on an administrator issues, connects and cuts off that person's keys (the operator's decision of 2026-11-12, recorded in ADR-0070 with the narrower rule it rejects). The Keys page and the Start page show the refusal by its code and message. `POST /v2/web/session/end` and the lead's sign-out read nothing of the key, so a denied person still signs out; they also still sign in and see their keys. Each of the three acts costs one more resolution of its key (two store calls for `<user>-web`, one for `<user>-admin`); no `GET` gained a read. Not changed: a denied `<user>-web` still asks for the person's deletion and reads their export.
