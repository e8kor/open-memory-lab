**Breaking for MCP clients: withdraw is a mode of `oml_write`, and the MCP server serves three tools.** [ADR-0083](adr/ADR-0083-the-memories-page-is-one-cockpit-with-approved-to-review-and-submitted-views-and-held-rows-never-appear-as-approved.md)'s amendment of d13 of 2026-11-24, decided by the operator: `oml_write {withdraw: <artifact_id>, reason?, idempotency_key}` withdraws a held write of the calling key's own on the same `POST /v1/memories/{artifact_id}/withdraw` call, with the same refusals (`memory.not_held`, `access.author_only`, `access.not_found`) and replay, and answers `{mode: "withdraw", artifact_id, state, idempotent_replay}`. Every other field beside `withdraw`, `text` included, is refused with `request.validation` naming it; `text` is required in every other mode and is no longer in the input schema's `required` list. `oml_withdraw` leaves `tools/list` and answers as an unknown tool, JSON-RPC -32602, with no alias. `tools/list` serves `oml_write`, `oml_read` and `oml_workspace`, as [ADR-0039](adr/ADR-0039-the-api-rewritten-for-v0-4-0.md) d2 does; the plugin's skill and README, the server instructions and the MCP reference follow. The HTTP route, `oml withdraw` and the console's Withdraw are unchanged ([upgrades](operations/upgrades.md)). A client permission rule that names `oml_withdraw`, a deny or ask rule included, protects nothing after the upgrade, and a rule that allows `oml_write` without a prompt now lets withdraw through without one too. `oml_write` with `artifact_id`, the old tool's argument, is refused with `request.validation` naming `/artifact_id`, saying that withdraw takes the id.
