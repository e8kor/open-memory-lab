Hardened `oml sync`'s git reads (#320, from the review of #318; ADR-0057 d6, ADR-0076 d9). `--rev=^HEAD` verified and came back as `^<id>`, so a later message read `docs/a.md is not a file at ^d63388d704b`; the resolved commit must now be a bare object id, and any other answer is refused by name (`did not resolve to one commit id`). The config reader no longer trims a value, so `"true "` is not read as the legacy `true` and `sync_consent_unbound` no longer warns for a value the opt-in cannot remove. A rev the server returns for an earlier sync is cut at a character, never at byte 12, so a multi-byte answer cannot panic the client. The tests now prove their names: the option-looking `--rev` test runs `oml` behind a `git` that logs its argv and asserts no `rev-parse` carries the rev, and the stand-in for git before 2.30 quotes the real git's path and answers `--end-of-options` as a real old git does (`fatal: Needed a single revision`, exit 128). Running the suite against a real git 2.25 and 2.7 in CI is not done.
