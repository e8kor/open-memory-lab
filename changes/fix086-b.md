**The v0.8.6 review's console, CLI and docs findings are fixed.** `oml keys issue-agent` takes `--reason` and `--create`, which puts `create` on its one write grant ([ADR-0097](adr/ADR-0097-every-admin-act-is-one-journalled-record-narrowing-takes-effect-at-once-widening-waits-on-a-second-admin-person-and-every-admin-key-belongs-to-a-person.md) d26, d31), and both `oml keys issue` and `issue-agent` ask for a reason on a terminal when none is given and print "waits on another admin" with the act id for a pending issuance; the `oml-admin:issue-agent-key` skill passes `--reason`. `oml_write`'s description no longer says a flagged child gets no grant of its own.

The workspace picker, Browse, the Memories cockpit and the personal workspace page label a public node "Public" ([ADR-0098](adr/ADR-0098-a-protected-or-frozen-workspace-can-be-marked-public-and-then-every-reading-key-in-the-tenant-reads-its-approved-items.md) d9). They draw a served path's placeholder for an unreadable private ancestor, `…`, as it is served: they never read it, link it or resolve it, and the cockpit's "Up to" says the parent is not readable.

The admin act confirm screen shows every part of an act that widens: a grant's `create` flag, the workspaces an issuance creates, an admin key's person and a time box's end. A public set also shows the workspace's path, its status and its children that stay private, and says that every reading key of the tenant, user keys included, recalls its approved items by default (ADR-0097 d23, d30, d31; ADR-0098 d9). On the admin Workspaces page, the Public toggle shows "waits on another admin" with the act's link while a set waits, and offers "Clear public", which declines the set. It also lists the node's public acts, from one read of `GET /v2/admin/acts` made beside the rows.

The administration To do lists each cleared public flag under "Done: public cleared", newest first, and leaves it out of the count (ADR-0098 d6).

The personal To do gains a **Notices** group. It lists each notice the person has not dismissed, with a Dismiss form, and the To do badge counts the notices (ADR-0097 d20, d24). The Rust SDK gains `notices` and `dismiss_notice` and reads `TodoCounts.notices`.

The admin key builder issues an admin key. With the admin role it names the key's admin person and sends `used_by: person` and no grants or limits, as `oml keys issue --role admin --person` does (ADR-0097 d21, d29).

The release marker for the maintenance key reads `KEY_ROLES`, a constant of the domain crate that a test holds to `Role`. A release tag whose role source declares no such constant is refused by name, and a unit test reads the real source (ADR-0097 d18, Production migration).

`docs/operations/upgrades.md` gains "Upgrade in order", the v0.8.6 procedure for a one-admin tenant whose CLI admin key is not linked. It covers the counts and what `admin_persons_ever` of 2 or more means, the token directory and mail settings, a deployer that knows the marker, the upgrade, convert-self, and link-self with acceptance within 30 days. It adds a subsection on the unlinked key's suspension and revocation, one on migrations 0070 to 0073 and 0077, and the `--person`/`--email` change to `oml bootstrap claim` and `oml quickstart`. The runbook says the operator verbs target the local replica and each replica keeps its own `operator.token_dir`.
