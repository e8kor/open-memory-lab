- **The web console runs only as its own process, and the landing ships on its own** ([ADR-0070](adr/ADR-0070-the-web-console-is-a-client-of-the-public-http-api-in-a-crate-that-cannot-reach-the-application-core.md), amended 2026-11-10). `oml-web` is a binary of its own over the public HTTP API at a required `web.api_url`; the in-process mode is dropped, and with it the dual mode. Caddy routes `/web/*` to `oml-web` and `/v1/*`, `/v2/*`, `/mcp`, `/oauth/*` and the sign-in routes to the server; local development runs both processes, started by `oml quickstart`. The middleware stack (request id and the page's audit line, session to `omls_` credential, CSRF, CSP, rate limit, error mapping) lives in `oml-web`, and a gateway in front is optional and trusted for none of it. The API accepts an `omls_` credential only from `oml-web`'s client identity, a web-client secret or mutual TLS, and never on `/mcp`. The budget is restated for a network hop: 5 ms p95 on loopback plus two round trips on a LAN, at most two sequential calls per page over pooled keep-alive connections, a timeout per call and partial-page failure states, unmeasured until [#170](https://github.com/e8kor/open-memory-lab/issues/170). The landing page is a separate deployable built from `site/` and released as `oml-site-<version>.tar.gz`.
