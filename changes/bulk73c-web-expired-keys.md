**Web console.** The Keys page, the admin's Keys page and the admin's People page mark an expired key and show its date and its rate (#337; ADR-0079 d2, d3, d4). Each key's row draws **expired** in the place and chip it draws `revoked` and `cut off`, the instant it expires or expired beneath its role, to the second and in UTC by name (`2026-10-29 12:30:00 UTC`, the instant as served in the element's `datetime`), and "N requests a minute" for a key that carries a rate of its own; a key with neither shows neither, and an admin key never carries either, so its row shows none. A key that carries two marks, such as `cut off` and `expired`, draws them apart, with a comma between them for a screen reader. Before, the pages read `revoked` and `cut_off` alone, so a key past its date read as live. An expired connector key is not offered **New connect code**, which the API refuses with `oauth.connect_refused` and reason `expired`; the row says "Expired: no new connect code until an admin sets a later date." instead. **Cut off** stays on an expired key: a denial is not refused on one, and an admin can move the date later. The page reads `expiry`, `expired` and `requests_per_minute` from `GET /v2/keys`, which already served them; no call was added. The page test holds each row equal to the API's fields for a key with both limits, a rate of one, an expired key, an expired connector key, a key with neither and the admin's own admin key. The pages were not looked at in a browser.
